条目按以下顺序排列：先是弥合"文档所宣称"与"代码所强制"之间差距的项（第 1–2 项），

每项说明当前行为、目标行为与涉及文件。严重度采用与[实验报告](实验报告.md)、

## 一、在提案闸门处强制证据不可变性 —— 严重度：高

**当前行为。** `src/blueprint/domain.py` 仅校验 `evidence_ref` 以 `trace://`、
`s3://` 或 `log://` 开头。它不要求 S3 引用固定 `versionId`、不要求指向审计桶、也不
要求位于提案人自己的前缀之下。

`bridge/server.py` 的 `memory_capture_evidence` 会返回一个固定版本的引用，且
`docs/桌面客户端集成设计.md` 第六章说明了正是版本固定使证据可验篡改。然而版本固定目前
是**捕获辅助工具**的一个属性，而非**接纳的前置条件**。携带未固定版本引用的提案会被接受；
其背后的对象随后可被覆盖写入，因为按设计覆盖同一 key 是允许的（被拒绝的是删除，不是
覆盖）。审核员在批准后顺着该引用查看，解析到的将是最新版本。

这是一处文档与代码的差距：不可变性被无条件宣称，但实际只在客户端配合时成立。

**目标行为。** 在校验期拒绝任何不满足以下三条的 `s3://` 证据引用：（a）携带
`versionId` 查询参数；（b）指向配置中的证据桶；（c）位于提案人自己的
`evidence/user:<sub>/` 前缀之下。桶名与前缀来自服务端配置与已认证的 `sub`，绝不取自
请求体。

**涉及文件。** `src/blueprint/domain.py`（校验）、
`src/handlers/propose_candidate.py`（传入预期桶名）、`tests/test_domain.py`、
`bridge/validate_bridge.py`（其"合格提案"用例目前使用未固定版本的引用，须同步更新，
否则将被新规则拒绝）。

## 二、把提案权与审批权分离 —— 严重度：高

**当前行为。** `src/handlers/reviewer_api.py` 仅按审核人组成员身份授权。没有任何检查
确认审批人不是提案人，且提案与审核由同一个 Cognito 用户池服务。审核人组的成员可以提出
一条陈述并自行批准。

由于人工审核是整个设计其余部分所依赖的控制点，自我审批通路会把双人保证降级为单人保证。

**目标行为。** 当决策的 `reviewer_id` 与候选项的 `proposer_actor_id` 相同时拒绝该决策，
并返回一个专用状态码，使该拒绝在日志与测试中可与授权失败区分开。对于审核人数量过少、
难以实施该规则的部署，将其做成部署参数，默认启用分离，并显式记录例外。

**平台侧已证明这条边界可以下沉到 IAM。** 上述方案是应用层校验；实测确认 AgentCore 在
Registry 上把提交与裁决拆成了两个独立 action，因而可由 IAM 强制而非依赖代码自觉：

| 凭证 | 尝试提案 | 尝试批准 |
|---|---|---|
| 仅持 `SubmitRegistryRecordForApproval` | 通过 | **AccessDeniedException** |
| 仅持 `UpdateRegistryRecordStatus` | **AccessDeniedException** | 通过 |

对本项目的含义是：提案 Lambda 与审核 Lambda 应持有互不重叠的 action 集合，使"提案者自批"
在 IAM 层就不可能，而不只是被应用代码拒绝。这属于 AWS 标准做法，实现代价不高，但需要拆分
现有的单一 reviewer Lambda —— 故列为演进方向而非立即改动。

**涉及文件。** `src/handlers/reviewer_api.py`、`tests/test_reviewer_api.py`、
`infra/lib/memory-governance-stack.ts`（拆分 Lambda 与策略）、
`docs/architecture.md` 的权限一节。

相关问题：审核人组成员校验发生在 Lambda 代码中，而非 API Gateway 授权方 —— 后者校验
token 但不校验组声明。把组校验移入 request authorizer 可消除对处理函数分发顺序的依赖。

## 三、先如实描述政策闸门的范围，再扩展它 —— 严重度：中

**当前行为。** `docs/architecture.md` 称含有原始凭据、受限数据或直接个人信息的候选项会
在人工审核前被拒。实际实现的闸门是
`privacy_classification != "restricted" and confidence >= 0.70`
（`src/blueprint/domain.py`）—— 一个自行申报的标签加一个自行申报的分值，没有任何内容
检测。一条被标为 `internal`、置信度 0.9 的凭据会进入审核队列。

实验中"0.98 置信度的 restricted 候选项仍被拦截"这一结果，证明的是**分级优先于置信度**，
而非内容检测。

**目标行为，分两步。** 第一步，修正文档，改为描述"基于申报分级的闸门"，因为当前措辞
夸大了实现。第二步，加入真正的审核前检查：针对凭据形态的模式匹配，以及在存储前和记忆
注入提示词前均应用 Bedrock Guardrail 策略。两份报告都已将 Guardrails 列为生产差距，
本项为其给出具体接入点。

**涉及文件。** `docs/architecture.md` 与 `docs/架构设计.md`（措辞）、
`src/blueprint/domain.py`（检查逻辑）、`src/handlers/propose_candidate.py`
（Guardrail 调用）。

## 四、取代机制：为已批准事实赋予有效性生命周期 —— 严重度：中

这是能力缺口最大、且完全没有部分实现的一项。

**当前行为。** 已批准的共享记录不可变，且**永久**有效 —— 先前此处写作"在 90 天资源过期
期限内"，该兜底不存在：`eventExpiryDuration` 按 event 在写入时生效，而共享记录经
`BatchCreateMemoryRecords` 直接创建，没有对应的 source event，`MemoryRecordCreateInput`
也没有任何 expiry 字段。记录级移除只有显式 `DeleteMemoryRecord` /
`BatchDeleteMemoryRecords`。没有
任何方式将其标记为不再为真。如果实验中批准的那条 curated-churn-view 约束在下个季度被
修正，旧记录仍可被检索，且与当前有效记录无法区分。记录级 TTL 不解决该问题：一条即将
过期的记录与一条新鲜记录在排序中等价，直到它消失的那一刻。

**平台已提供的能力。** 该项无需离开 AgentCore 即可实现：

- `BatchUpdateMemoryRecords` 接受 `memoryRecordId`、`content`、`metadata`、
  `namespaces` 与 `timestamp`，因此可重写既有记录的元数据。
- `DeleteMemoryRecord` 与 `BatchDeleteMemoryRecords` 提供硬删除能力。
- 记忆记录流式（memory record streaming）向 Kinesis 推送创建、更新与删除事件，其中
  包含由 consolidation 去重与取代所引发的删除。

**可用的过滤能力。** 元数据过滤支持十个操作符：`EQUALS_TO`、`EXISTS`、`NOT_EXISTS`、
`BEFORE`、`AFTER`、`CONTAINS`、`GREATER_THAN`、`GREATER_THAN_OR_EQUALS`、`LESS_THAN`、
`LESS_THAN_OR_EQUALS`（botocore 1.43.58 服务模型）。**注意 SDK 版本**：早于本仓库
`src/requirements.txt` 所 pin 的 `boto3>=1.43.36` 的版本只有前三个，因此在旧 SDK 上编写
的范围过滤会被本地校验拒绝。

由于 `BEFORE`/`AFTER` 存在，有效性窗口**可以**表达为对时间戳的过滤。但本蓝图仍建议把
取代建模为**离散状态标志**，理由不是能力缺失而是审计：

- 通过 `BatchUpdateMemoryRecords` 为旧记录增加 `superseded_by`，并把 `review_status`
  置为诸如 `superseded` 的终态值。
- 检索侧已按 `review_status = approved` 过滤（`src/agent/context_builder.py`），因此
  被取代的记录会自动离开可检索集合，查询路径无需任何改动。
- 两条记录都保留。审计链要求知道团队曾经相信什么、以及从何时起相信，硬删除会摧毁这一点。

**状态值应沿用 AgentCore 已有的命名，而不是自创。** AgentCore Registry 的审批状态机里
已经有一个终态叫 `DEPRECATED`，且实测确认它**在平台侧就是终态** —— 对处于该状态的记录
再做任何状态变更都会被拒：

```
Cannot update registry record in DEPRECATED status (terminal state)
```

这一点值得借鉴的不是 API，而是**它对"取代"的建模选择**：被取代的知识不被删除，而是转入
一个不可再变的终态，从而既离开当前有效集合、又留在审计记录里。这与上文"两条记录都保留"
的论证同向，且给出了官方词汇 —— 所以本项目应采用 `DEPRECATED` 而非自造
`superseded`，理由是同一个概念在同一个服务里应当只有一个名字。

**但只借鉴命名与终态语义，不照搬转换规则。** 实测 Registry 的转换矩阵后发现两处不适用于
知识治理的行为：`REJECTED → APPROVED` 是允许的（一次驳回可被静默覆盖，无需重新审核），
`APPROVED → APPROVED` 重放也成功。本项目的一次性回调令牌在重放时返回 409（见
[实验报告](实验报告.md)检查 11），在这一点上比 Registry 更严，不应向其对齐。

**让该决策走既有审核工作流，而不是交给模型。** 在候选项契约中增加可选字段
`supersedes: <record_id>`。批准这类候选项时，在同一工作流分支内发布新记录并把旧记录翻转
为 `DEPRECATED`。由审核员决定什么取代什么。

最后这一点是刻意的。自动矛盾检测是同类系统中最薄弱的环节：某图式记忆系统所报告的冲突
消解得分之所以是其最低类别，恰恰因为矛盾判断是一次 LLM 调用
（[arXiv:2606.01435](https://arxiv.org/html/2606.01435)）；而关于陈旧知识处理的研究
报告称，前沿模型对隐式失效（一条事实被否定但无显式矛盾）处理不佳，且常直接接受问题中
嵌入的陈旧前提（[arXiv:2605.06527](https://arxiv.org/abs/2605.06527)）。本蓝图已具备
带审计链的人工决策点；扩展它的代价是一个字段加一个工作流分支，同时避免引入一个不可靠的
裁决器。

作为对照，完整时间建模的参考设计是 Zep/Graphiti 的双时间边模型，它把"事实何时为真"与
"系统何时知道"分离，并采用失效而非删除
（[arXiv:2501.13956](https://arxiv.org/abs/2501.13956)）。Zep 当前产品文档明确提供
Fact Invalidation：新数据推翻旧事实时，失效时刻被记录在该事实的边上。**这是 AgentCore
目前没有的能力**，也是本项目为何必须自己实现取代机制的原因。

一个必须写明的事实分歧：AWS 机器学习博客称 consolidation 会"把过时记忆标记为 INVALID
而非立即删除，从而维持不可变审计线索"，但 API 参考中的 `MemoryRecord` 只有
`content`/`createdAt`/`memoryRecordId`/`memoryStrategyId`/`namespaces`/`metadata`
六个字段，**没有任何状态或有效性字段**；记忆记录流式的事件类型只有
`MemoryRecordCreated`/`MemoryRecordUpdated`/`MemoryRecordDeleted`，且文档把 consolidation
的取代归入**删除**路径。也就是说 AWS 自己的博客与自己的 API 文档不一致。本蓝图按 API
文档行事：**不依赖任何平台侧的 INVALID 语义**，审计线索由候选表与 Kinesis 流式自行保留。
（`MemoryRecordOutput` 上确有 `MemoryRecordStatus`，但那是批量写操作的返回状态
SUCCEEDED/FAILED，不是记录生命周期状态，不可引为失效依据。）

**涉及文件。** `contracts/memory-candidate-proposed.json`、`src/blueprint/domain.py`、
`src/blueprint/memory.py`（在发布路径之外增加更新路径）、
`src/handlers/publish_shared.py`、`infra/lib/memory-governance-stack.ts`（发布器角色
需在同一精确命名空间条件下获得 `BatchUpdateMemoryRecords`）、`dashboard/`（将被取代的
记录区分展示）。`superseded_by` 已作为索引键声明（`infra/lib/memory-governance-stack.ts`）：
索引键**可以**后加（`UpdateMemory` 的 `--add-indexed-keys`），但不可删除、且不回填 ——
只有键存在之后写入或更新的记录才被索引，因此提前声明使这段时间内批准的记录在取代机制上线
后仍可被过滤。

## 五、提案的触发时机与判断标准 —— 严重度：高

**这一项是整套论证的前提，不是待办。** 审批链路完整而捕获触发点缺失，意味着治理链路的
瓶颈从来不在中间那一段；本仓库自身即为标本 —— 实验报告中的候选项均由脚本产生，而
`skills/` 目录自创建以来只有新增、没有一次修改。

**当前行为。** 提案契约本身是完整的：五种 `category`、置信度、隐私分级、`promotion_hint`
与不可变 `evidence_ref` 都在 `src/blueprint/domain.py` 中强制校验。但**没有任何机制告诉
模型何时该提案、以及什么内容够格提案**。

`memory_propose_shared` 是一个普通 MCP 工具，由模型自主决定调用时机，其唯一依据是工具的
描述。判断标准现已写入该描述（见下方第 1 条），但**触发时机仍无机制**：仓库中不存在 hook
在每轮结束后评估是否值得提案，`skills/` 中唯一的 Skill 与提案判断无关。因此提案仍依赖
用户显式要求，或模型自行留意。

这构成一个可用性缺口而非安全缺口，但影响面更大：**若无人提案，整套治理机制空转** ——
审核队列长期为空，共享记忆无法积累。实验报告中的候选项均由脚本直接调用 API 产生，而非
智能体自主提出。

**目标行为，四条改动。** 第 1、2 条针对提案本身，第 3、4 条针对触发时机 —— 后两条是
2026-08-18 讨论的结论，尚未实现。

1. **把判断标准传达给模型 —— 已完成。** `memory_propose_shared` 的 docstring 现在逐条
   定义五个 `category` 的语义（`fact` 是独立于任务成立的观察；`decision` 含它排除了什么；
   `constraint` 指违反后会静默产生错误答案的口径陷阱；`incident` 指已确认的故障及其成因；
   `procedure_hint` 指值得复用的操作步骤），并明确列出**不该提案**的内容：自己的格式与
   工具偏好、单一任务的细节、复述文档、以及未经验证的猜测。同时说明了置信度不应为了
   通过闸门而抬高、`restricted` 分级何时必须使用，以及应先调 `memory_capture_evidence`
   获取版本固定引用。`bridge/validate_bridge.py` 增加了一条断言，校验五个枚举的**语义**
   （而非仅名称）确实出现在 `tools/list` 返回的描述中 —— 否则这项改动可能被无声回退。
2. **用 hook 自动捕获证据 —— 未完成。** 当前模型仍须先调 `memory_capture_evidence` 换取
   `s3://` 引用、再调 `memory_propose_shared`，跳过第一步会因证据校验失败被拒 —— 安全但
   体验不佳（已记录于[桌面客户端集成设计](桌面客户端集成设计.md)第十一章）。由 hook 在每轮
   结束后自动落证据，可使 evidence 始终就绪，模型只需判断"这条是否值得提"。

3. **提案判断 Skill：把贡献成本压到最低的那一刻 —— 未完成。** 新增一个 `skills/` 下的
   记忆 Skill，指导智能体识别「多轮澄清后终于说清楚」的对话 —— 一个口径被反复追问后确定、
   一次故障被定位到成因、一个约束被试错后确认 —— 并在这类时刻提示用户提案，而不是等用户
   自己想起来。**这条不只是体验改进，它是唯一能保住署名链的路径**：陈述由当事人给出，
   `evidence_ref` 指向那次真实对话，`proposer_actor_id` 仍由服务端从 token 的 `sub` 派生。
   已有第三方生产验证走的是同一条路：把审批移到捕获时刻、由贡献者自己完成
   （见[定位分析](定位分析.md)「四、审核者产出与疲劳」，该来源未核实）。
4. **定时智能体：只调度注意力，不产出提案 —— 未完成。** 一个管理员角色或定时任务可以发现
   「哪些问题被反复问到」，但**它不应该自己提案**。理由是可归因性：提案要么署智能体自己
   （「谁写的、依据是什么」就断了），要么署某个用户（那是伪造）；而它的证据只能指向聚合
   统计，不是一段可回溯的对话。**因此它的产出是一份话题清单，交给第 3 条的 Skill 在下一次
   有人真正讲清该话题时使用。**

**定时智能体不需要读取任何记忆内容 —— 这是隐私边界能守住的原因。** 它的数据源是
`src/agent/context_builder.py` 写出的检索指标（CloudWatch 日志），不是 Memory：

| | 扫描长期记忆 | 扫描检索指标 |
|---|---|---|
| 所需权限 | 跨 actor 读取所有人个人记忆 | `logs:FilterLogEvents` |
| 可见内容 | 记忆原文 | 逐 token 哈希集合与命中数 |
| 隐私边界 | **破坏 `actorId` 条件键的隔离前提** | 无个人数据可读 |
| 噪声 | 高 | 已降维 |

一个能跨 actor 读取全部个人记忆的角色，需要的正是 IAM 条件键刻意不授予的权限 —— 而本蓝图
在别处正是引 Databricks 那句 "The app service principal can read every scope." 来批评这种
设计。自己再造一个，论证就自己塌了。指标路径不存在这个问题：敏感信息在写入日志之前就已经
被哈希掉，不是靠访问控制事后遮挡。

**共享层与个人层要分开说。** 已审核的共享记录本就对团队可见，管理员智能体扫描它没有隐私
问题 —— 去重、发现该晋升的条目，都应该扫。边界只在个人层。

**提示频率本身就是习惯化风险。** 若 Skill 每轮都问「要不要沉淀一下」，用户会很快学会无脑
跳过，于是得到一个看起来在工作、实际全是噪声的入口 —— 这与 README 限制章节记录的审核疲劳
是同一机制。**所以第 4 条的价值不在于发现更多话题，而在于让提示变稀少**：稀少才有精度。

**四条改动的分工。** 第 1 条解决判断标准（已做），第 2 条消除前置负担（待做），第 3 条解决
触发时机（待做），第 4 条为第 3 条提供频率闸门（待做）。

**冷启动次序是硬约束。** 检索指标目前尚无数据，因此第 3 条必须先以模型自身判断上线、容忍
一段噪声期，等指标积累出量再切换为闸门。反过来不成立：指标没有数据时，Skill 至少还能靠
模型判断工作。

**待办涉及文件。** `.mcp.json` 与 hook 配置（证据自动捕获）；`skills/` 新增提案判断 Skill；
`poc/analyze_retrieval_metrics.py`（供定时智能体消费的话题清单输出）。

> **先修埋点的三处缺陷，否则第 4 条建立在坏数据上。** 一、`fingerprint_query` 的分词是
> `[a-z0-9]+`，**对中文完全无效**（切不出词即为空集），而桌面路径的提问以中文为主；
> 二、指纹只能识别措辞相近的重复，识别不了换了说法的同义提问，要后者就得存 embedding，
> 而那不再是不可逆的；三、埋点目前只在 `src/agent/context_builder.py`（Runtime 路径），
> **桌面 bridge 侧尚未接入，而那是主要流量** —— 且两侧的指纹算法必须完全一致，否则同一个
> 问题在两条路径上产生不同哈希，跨路径重复检测失效。这是正确性问题，不是代码风格问题。

> `poc/runtime_agent.py` 不在此列：它没有任何提案工具，其 system prompt 只负责消费共享
> 记忆。提案能力目前只存在于桌面 bridge。

## 六、新鲜度信号与上下文预算 —— 严重度：中

**当前行为。** `src/agent/context_builder.py` 请求固定的 `topK` 并注入返回结果。记录
年龄是可得的 —— `RetrieveMemoryRecords` 为每条记录返回 `createdAt` —— 但未用于排序、
展示或复审触发。对进入提示词的记忆总量也没有上限。

**目标行为。** 三项可分离的改动：

- **在注入处呈现年龄。** 为每条被注入的共享记录标注其 `createdAt`，使模型以及任何查看
  链路追踪的人能看出某条陈述已有八个月之久。这是纯展示层改动，无检索成本。
- **按年龄触发复审。** 周期性发出事件，把超过可配置年龄的已批准记录列入审核队列，供
  确认或取代。这让第 4 项由被动变为主动。
- **限定上下文预算。** 把注入记录条数做成带文档化默认值的配置参数，因为保留与整合之间
  的权衡取决于预算（[arXiv:2607.17545](https://arxiv.org/html/2607.17545v1)）。

刻意不做的事：按年龄自动删除。衰减应体现在排序与复审触发中，而不是静默移除已审计记录。

## 七、清理残留的真空断言 —— 严重度：中

两份报告都记录了同一条方法论教训：安全类断言必须既验证"该拦的拦住了"，也验证"该有的
确实有"，并且必须核对失败的**原因**而不只是失败是否发生。若干检查目前尚未达到该标准。

- `bridge/validate_bridge.py`：证据篡改类断言判断的是 `!= "ALLOWED"`，任何
  `ClientError` 都能满足 —— 包括桶名拼错或 `NoSuchBucket`。应断言 `== "AccessDenied"`。
- `bridge/validate_bridge.py`：非审核员被拒一项仅断言 `ok is False`，而 DNS 失败、
  404 或 500 同样满足。应断言 403。
- `bridge/validate_bridge.py`：跨用户检查中基于空命名空间的旧版检查，与替代它的直接
  权限探测一并保留。探测才是真正的检查；保留较弱的那条会虚增计数。
- `bridge/server.py`：`AccessDeniedException` 无论起因都被报告为跨用户或共享写入越界，
  于是 KMS 或配置错误会被叙述为一次越界尝试。应报告实际错误码。
- `infra/test/`：CDK 测试大多是 `JSON.stringify(template).toContain(...)` 子串检查。
  README 中最强的那条论断 —— Runtime 角色对共享记忆不持有任何写 action —— 没有任何
  测试覆盖。应为其补充断言，并同时覆盖：任何 `bedrock-agentcore:` action 上不得出现
  `Resource: "*"`、两张 DynamoDB 表的 KMS 加密，以及部署说明所依赖的 `RETAIN` 移除
  策略。

## 八、为审核补超时升级路径 —— 严重度：高

**依据。** 这一项不是自查发现的，而是 AWS Well-Architected Agentic AI Lens 明确要求的。
[AGENTSEC04-BP02](https://docs.aws.amazon.com/wellarchitected/latest/agentic-ai-lens/agentsec04-bp02.html)
把"无超时策略或升级路径"直接列为反模式：

> "Implementing approval workflows **without timeout policies or escalation paths**, so
> agent execution stalls indefinitely when reviewers are unavailable."

并给出实现要求：

> "In Step Functions, TimeoutSeconds or HeartbeatSeconds on the task state waiting for the
> approval token triggers a timeout transition, and **Catch clauses route timed-out
> executions to an escalation state** (notify secondary reviewers, escalate to management,
> or **default to a safe fallback, typically blocking the operation**)."

**当前行为。** `WaitForHumanReview` 设了 7 天 `taskTimeout`
（`infra/lib/memory-governance-stack.ts`），但没有 `addCatch`。超时后执行以未捕获错误
失败，候选项**永久停留在 `PENDING_REVIEW`** —— 候选表无终态写入，审核队列会一直显示它
待审，而工作流已经死亡。开发过程中确实出现过一个由此卡死的执行，并且它阻塞了
CloudFormation 的资源清理。

**目标行为。** 为该状态添加 `addCatch` 捕获 `States.Timeout`，路由到新的 `MarkTimedOut`
终态，写入明确状态（如 `REVIEW_TIMED_OUT`）。安全兜底是拒绝而非放行 —— 未获批准的知识
不得进入共享记忆。回调记录也应一并收敛，避免 `WAITING` 行长期滞留。

**涉及文件。** `infra/lib/memory-governance-stack.ts`（`createReviewWorkflow`）、
`src/handlers/mark_status.py`、`infra/test/memory-governance-stack.test.ts`。

## 九、按 AGENTSEC01 成熟度模型自评并补齐 —— 严重度：中

**依据。**
[AGENTSEC01 Secure agent memory and state](https://docs.aws.amazon.com/wellarchitected/latest/agentic-ai-lens/agentsec01.html)
给出五级成熟度模型，可作为本项目的外部标尺，而非自定义评分。

**当前定级。** 逐条对照后，本项目落在 **Level 3 与 Level 5 之间**：

| 级别 | 要求 | 本项目 |
|---|---|---|
| 3 | 分层命名空间（per-actor / per-session 占位符） | 已具备 |
| 3 | 多层校验：schema + Guardrails 策略与 PII 过滤 + 高风险输出的上下文接地检查 | **仅 schema 与申报标签**；无 Guardrails、无 PII 过滤、无接地检查 |
| 4 | 每次读取做 KMS 支撑的 HMAC 完整性校验 | **未实现** |
| 4 | 所有写入路径共用同一校验管线（含工具输出、智能体间消息） | 部分：共享路径有闸门，个人记忆写入无 |
| 4 | CloudWatch 异常检测 + 经 EventBridge 的幻觉熔断广播 | **未实现** |
| 5 | 例行红队演练模拟投毒与传播 | **未实现** |
| 5 | 记忆治理可编码可审计 | 已具备（本项目核心） |

**值得注意的错位。** 本项目已达 Level 5 的"治理可编码可审计"，却缺 Level 3 的 Guardrails
与 Level 4 的完整性校验。这说明本项目沿治理维度走得深，而在内容安全与运行时完整性维度上
仍浅 —— 与[实验报告](实验报告.md)第九章"政策闸门只读申报标签、不检查内容"是同一件事，
此处由外部标尺给出了独立确认。

**目标行为。** 按优先级补齐：先做 Guardrails 与 PII 过滤（Level 3，同时收敛第 3 项的
政策闸门范围），再做红队演练（Level 5，可直接复用
[MINJA](https://arxiv.org/abs/2503.03704) 与
[GhostWriter](https://arxiv.org/abs/2607.06595) 的手法验证投毒抵抗力）。HMAC 逐读校验
（Level 4）成本较高，应在明确威胁模型后再评估。

**涉及文件。** `src/blueprint/domain.py`（闸门）、`infra/lib/memory-governance-stack.ts`
（Guardrails 接入）、新增红队验证脚本。

## 其他值得处理的事项

- **不引入 `DRAFT` 状态，理由记录在此。** Registry 的状态机以 `DRAFT` 起始，让提案者先建
  记录、再自行决定何时提交审批。本项目曾考虑对齐，结论是不必要：桌面端的
  `memory_capture_evidence` 已经是与提案分离的一步，且 `memory_propose_shared` 强制要求
  `evidence_ref` 指向不可变记录，因此"先攒够证据再提交"这一场景已由工具边界满足，无需在
  候选生命周期里再加一个状态。多加一个状态会让状态机与审核队列的语义都变复杂，而换不到
  新能力。

- **移除 `USER_PASSWORD_AUTH`。** `infra/lib/memory-governance-stack.ts` 同时启用了
  `userPassword` 与 `userSrp`。仅 SRP 即已足够，密码流是不必要的攻击面。bridge 使用
  密码认证已被记为 POC 差距；改用带 PKCE 的授权码流可彻底消除对该流的需求。
- **重新考虑证据桶的 deny 语句。** 该策略使用 `NotPrincipal` 搭配
  `AccountRootPrincipal`。AWS 指引对此模式推荐使用 `aws:PrincipalArn` 上的
  `ArnNotEquals`；当前写法豁免的范围超出预期。真正提供不可变性的机制是第 1 项中的
  版本固定引用，桶策略不应被描述得像是它在提供该保证。
- **校验 bridge 的 `session_key`。** 它由客户端提供，且未经校验即进入摘要策略的
  `{sessionId}` 命名空间模板。检索条件把爆炸半径限制在调用方自己的子树内，但"没有任何
  工具接受 namespace 参数"这一说法仅在参数名层面成立。
- **约束审核 API 的候选项列举。** 目前使用 Scan；候选量增长后改用 status GSI 是已记录
  的后续项。
- **按写入路径拆分共享记忆。** 人工撰写的流程性知识与 LLM 抽取的团队事实是不同的治理
  对象，可能需要不同的闸门。Anthropic 将 `CLAUDE.md` 记录为纳入版本控制的流程性记忆，
  与智能体自写记忆并行运作；Thomson Reuters 描述了把已验证方法提升为可审阅的
  `SKILL.md`、卡在知识管理员控制的审批之后并做版本化
  （[Thomson Reuters](https://blogs.thomsonreuters.com/legal-blog/fiduciary-standards-for-legal-agentic-memory-systems/)）。
  `skills/` 目录已代表该去向，但这一区分尚未在 `docs/architecture.md` 中表述为显式的
  治理边界。

## 定位说明

共享作用域原语在生态中普遍存在 —— group graph、共享记忆块、多 scope 标签、命名空间
元组 —— 但它们放宽的是读写作用域，而非对写入设闸。托管产品提供的是事后策展，例如记忆
CRUD 界面与删除 API，用于在坏记录落库之后加以修正。截至 2026 年 7 月，在所调研的产品
中，未发现将自动化的事前闸门、人工审批与 IAM 强制隔离组合为原生能力的实现。

这一缺位正被独立地指出：一篇从计算机体系结构视角讨论多智能体记忆的文章，将缺失的
*agent memory access protocol*（定义读写语义、权限、作用域与粒度）列为两块缺位协议
之一（[SIGARCH](https://www.sigarch.org/multi-agent-memory-from-a-computer-architecture-perspective-visions-and-challenges-ahead/)）；
而上述 Thomson Reuters 的主张，是从职业责任而非平台能力的论证出发，抵达了"审批闸门 +
版本化的流程性记忆"这一相同结论。

这是用于确定优先级的背景，而非新颖性主张：真正的贡献是治理模型本身，而第 1 至 4 项
决定了它在被对抗性阅读（而非配合性阅读）时是否依然成立。
