# 下一步演进

> 本文档为主版本。English: [roadmap.md](roadmap.md)。
> 相关：[设计取舍依据](设计取舍依据.md) · [架构设计](架构设计.md)

条目按以下顺序排列：先是弥合"文档所宣称"与"代码所强制"之间差距的项（第 1–2 项），
其次是把治理模型扩展到尚未覆盖的维度、以及让它真正被用起来（第 3–6 项），最后是加固
验证方法本身（第 7 项）。

每项说明当前行为、目标行为与涉及文件。严重度采用与[实验报告](实验报告.md)、
[桌面客户端集成设计](桌面客户端集成设计.md)中生产差距表相同的标度。

## 一、在提案闸门处强制证据不可变性 —— 严重度：高

**当前行为。** `src/blueprint/domain.py` 仅校验 `evidence_ref` 以 `trace://`、
`s3://` 或 `log://` 开头。它不要求 S3 引用固定 `versionId`、不要求指向审计桶、也不
要求位于提案人自己的前缀之下。

`bridge/server.py` 的 `memory_capture_evidence` 会返回一个固定版本的引用，且
`docs/桌面客户端集成设计.md` 第六章说明了正是版本固定使证据可验篡改。然而版本固定目前
是**捕获辅助工具**的一个属性，而非**接纳的前置条件**。携带未固定版本引用的提案会被接受；
其背后的对象随后可被覆盖写入，因为按设计覆盖同一 key 是允许的（被拒绝的是删除，不是
覆盖）。审核员在批准后顺着该引用查看，解析到的将是最新版本。

这是一处文档与代码的差距：不可变性被无条件宣称，但实际只在客户端配合时成立。

**目标行为。** 在校验期拒绝任何不满足以下三条的 `s3://` 证据引用：（a）携带
`versionId` 查询参数；（b）指向配置中的证据桶；（c）位于提案人自己的
`evidence/user:<sub>/` 前缀之下。桶名与前缀来自服务端配置与已认证的 `sub`，绝不取自
请求体。

**涉及文件。** `src/blueprint/domain.py`（校验）、
`src/handlers/propose_candidate.py`（传入预期桶名）、`tests/test_domain.py`、
`bridge/validate_bridge.py`（其"合格提案"用例目前使用未固定版本的引用，须同步更新，
否则将被新规则拒绝）。

## 二、把提案权与审批权分离 —— 严重度：高

**当前行为。** `src/handlers/reviewer_api.py` 仅按审核人组成员身份授权。没有任何检查
确认审批人不是提案人，且提案与审核由同一个 Cognito 用户池服务。审核人组的成员可以提出
一条陈述并自行批准。

由于人工审核是整个设计其余部分所依赖的控制点，自我审批通路会把双人保证降级为单人保证。

**目标行为。** 当决策的 `reviewer_id` 与候选项的 `proposer_actor_id` 相同时拒绝该决策，
并返回一个专用状态码，使该拒绝在日志与测试中可与授权失败区分开。对于审核人数量过少、
难以实施该规则的部署，将其做成部署参数，默认启用分离，并显式记录例外。

**涉及文件。** `src/handlers/reviewer_api.py`、`tests/test_reviewer_api.py`、
`docs/architecture.md` 的权限一节。

相关问题：审核人组成员校验发生在 Lambda 代码中，而非 API Gateway 授权方 —— 后者校验
token 但不校验组声明。把组校验移入 request authorizer 可消除对处理函数分发顺序的依赖。

## 三、先如实描述政策闸门的范围，再扩展它 —— 严重度：中

**当前行为。** `docs/architecture.md` 称含有原始凭据、受限数据或直接个人信息的候选项会
在人工审核前被拒。实际实现的闸门是
`privacy_classification != "restricted" and confidence >= 0.70`
（`src/blueprint/domain.py`）—— 一个自行申报的标签加一个自行申报的分值，没有任何内容
检测。一条被标为 `internal`、置信度 0.9 的凭据会进入审核队列。

实验中"0.98 置信度的 restricted 候选项仍被拦截"这一结果，证明的是**分级优先于置信度**，
而非内容检测。

**目标行为，分两步。** 第一步，修正文档，改为描述"基于申报分级的闸门"，因为当前措辞
夸大了实现。第二步，加入真正的审核前检查：针对凭据形态的模式匹配，以及在存储前和记忆
注入提示词前均应用 Bedrock Guardrail 策略。两份报告都已将 Guardrails 列为生产差距，
本项为其给出具体接入点。

**涉及文件。** `docs/architecture.md` 与 `docs/架构设计.md`（措辞）、
`src/blueprint/domain.py`（检查逻辑）、`src/handlers/propose_candidate.py`
（Guardrail 调用）。

## 四、取代机制：为已批准事实赋予有效性生命周期 —— 严重度：中

这是能力缺口最大、且完全没有部分实现的一项。

**当前行为。** 已批准的共享记录不可变，且在 90 天资源过期期限内实质上永久有效。没有
任何方式将其标记为不再为真。如果实验中批准的那条 curated-churn-view 约束在下个季度被
修正，旧记录仍可被检索，且与当前有效记录无法区分。记录级 TTL 不解决该问题：一条即将
过期的记录与一条新鲜记录在排序中等价，直到它消失的那一刻。

**平台已提供的能力。** 该项无需离开 AgentCore 即可实现：

- `BatchUpdateMemoryRecords` 接受 `memoryRecordId`、`content`、`metadata`、
  `namespaces` 与 `timestamp`，因此可重写既有记录的元数据。
- `DeleteMemoryRecord` 与 `BatchDeleteMemoryRecords` 提供硬删除能力。
- 记忆记录流式（memory record streaming）向 Kinesis 推送创建、更新与删除事件，其中
  包含由 consolidation 去重与取代所引发的删除。

**约束解法的一项设计限制。** 检索的元数据过滤仅支持 `EQUALS_TO`、`EXISTS` 与
`NOT_EXISTS`（已对 `bedrock-agentcore` 服务模型核实，API 版本 2024-02-28）。不存在
范围操作符，因此有效性窗口无法表达为对时间戳的过滤。取代机制因此必须建模为**离散状态
标志**，而非日期比较：

- 通过 `BatchUpdateMemoryRecords` 为旧记录增加 `superseded_by`，并把 `review_status`
  置为诸如 `superseded` 的终态值。
- 检索侧已按 `review_status = approved` 过滤（`src/agent/context_builder.py`），因此
  被取代的记录会自动离开可检索集合，查询路径无需任何改动。
- 两条记录都保留。审计链要求知道团队曾经相信什么、以及从何时起相信，硬删除会摧毁这一点。

**让该决策走既有审核工作流，而不是交给模型。** 在候选项契约中增加可选字段
`supersedes: <record_id>`。批准这类候选项时，在同一工作流分支内发布新记录并翻转旧记录
状态。由审核员决定什么取代什么。

最后这一点是刻意的。自动矛盾检测是同类系统中最薄弱的环节：某图式记忆系统所报告的冲突
消解得分之所以是其最低类别，恰恰因为矛盾判断是一次 LLM 调用
（[arXiv:2606.01435](https://arxiv.org/html/2606.01435)）；而关于陈旧知识处理的研究
报告称，前沿模型对隐式失效（一条事实被否定但无显式矛盾）处理不佳，且常直接接受问题中
嵌入的陈旧前提（[arXiv:2605.06527](https://arxiv.org/abs/2605.06527)）。本蓝图已具备
带审计链的人工决策点；扩展它的代价是一个字段加一个工作流分支，同时避免引入一个不可靠的
裁决器。

作为对照，完整时间建模的参考设计是 Graphiti 的双时间边模型，它把"事实何时为真"与
"系统何时知道"分离，并采用失效而非删除
（[arXiv:2501.13956](https://arxiv.org/abs/2501.13956)）。状态标志是该模型在
仅支持 `EQUALS_TO` 过滤条件下可表达的子集。

**涉及文件。** `contracts/memory-candidate-proposed.json`、`src/blueprint/domain.py`、
`src/blueprint/memory.py`（在发布路径之外增加更新路径）、
`src/handlers/publish_shared.py`、`infra/lib/memory-governance-stack.ts`（发布器角色
需在同一精确命名空间条件下获得 `BatchUpdateMemoryRecords`）、`dashboard/`（将被取代的
记录区分展示）。

## 五、提案的触发时机与判断标准 —— 严重度：高

**当前行为。** 提案契约本身是完整的：五种 `category`、置信度、隐私分级、`promotion_hint`
与不可变 `evidence_ref` 都在 `src/blueprint/domain.py` 中强制校验。但**没有任何机制告诉
模型何时该提案、以及什么内容够格提案**。

`memory_propose_shared` 是一个普通 MCP 工具，由模型自主决定调用时机，其唯一依据是工具的
docstring。仓库中不存在 hook（每轮结束后自动评估）、`skills/` 中唯一的 Skill 与提案判断
无关、`poc/runtime_agent.py` 的 system prompt 也完全未提及提案。五个 `category` 枚举的
**名称**通过校验错误信息对模型可见（`bridge/server.py` 的 `CATEGORIES`），但**语义从未
传达** —— 模型不知道什么算 `constraint`、什么算 `incident`、更不知道个人偏好与一次性任务
细节不应提案。

这构成一个可用性缺口而非安全缺口，但影响面更大：**若无人提案，整套治理机制空转** ——
审核队列长期为空，共享记忆无法积累。实验报告中的候选项均由脚本直接调用 API 产生，而非
智能体自主提出。

**目标行为，两条独立改动。**

1. **把判断标准传达给模型。** 五个枚举已隐含了标准，将其语义写进工具描述或一个专门的
   Skill：`fact` 与 `decision` 需可独立理解且对他人有效；`constraint` 指口径陷阱一类的
   硬约束；`incident` 指已发生并被确认的故障；`procedure_hint` 指可复用的操作要点。同时
   明确**不该提案**的内容：个人偏好、一次性任务细节、未经验证的猜测。这是成本最低的一步。
2. **用 hook 自动捕获证据。** 当前模型必须先调 `memory_capture_evidence` 换取 `s3://`
   引用、再调 `memory_propose_shared`，跳过第一步会因证据校验失败被拒 —— 安全但体验不佳
   （已记录于[桌面客户端集成设计](桌面客户端集成设计.md)第十一章）。由 hook 在每轮结束后
   自动落证据，可使 evidence 始终就绪，模型只需判断"这条是否值得提"。

两条改动的分工：第 2 条消除前置负担，第 1 条解决判断本身。

**涉及文件。** `bridge/server.py`（`memory_propose_shared` 的 docstring）、
`skills/`（新增一个提案判断 Skill）、`poc/runtime_agent.py`（system prompt）、
`.mcp.json` 与 hook 配置（证据自动捕获）。

## 六、新鲜度信号与上下文预算 —— 严重度：中

**当前行为。** `src/agent/context_builder.py` 请求固定的 `topK` 并注入返回结果。记录
年龄是可得的 —— `RetrieveMemoryRecords` 为每条记录返回 `createdAt` —— 但未用于排序、
展示或复审触发。对进入提示词的记忆总量也没有上限。

**目标行为。** 三项可分离的改动：

- **在注入处呈现年龄。** 为每条被注入的共享记录标注其 `createdAt`，使模型以及任何查看
  链路追踪的人能看出某条陈述已有八个月之久。这是纯展示层改动，无检索成本。
- **按年龄触发复审。** 周期性发出事件，把超过可配置年龄的已批准记录列入审核队列，供
  确认或取代。这让第 4 项由被动变为主动。
- **限定上下文预算。** 把注入记录条数做成带文档化默认值的配置参数，因为保留与整合之间
  的权衡取决于预算（[arXiv:2607.17545](https://arxiv.org/html/2607.17545v1)）。

刻意不做的事：按年龄自动删除。衰减应体现在排序与复审触发中，而不是静默移除已审计记录。

## 七、清理残留的真空断言 —— 严重度：中

两份报告都记录了同一条方法论教训：安全类断言必须既验证"该拦的拦住了"，也验证"该有的
确实有"，并且必须核对失败的**原因**而不只是失败是否发生。若干检查目前尚未达到该标准。

- `bridge/validate_bridge.py`：证据篡改类断言判断的是 `!= "ALLOWED"`，任何
  `ClientError` 都能满足 —— 包括桶名拼错或 `NoSuchBucket`。应断言 `== "AccessDenied"`。
- `bridge/validate_bridge.py`：非审核员被拒一项仅断言 `ok is False`，而 DNS 失败、
  404 或 500 同样满足。应断言 403。
- `bridge/validate_bridge.py`：跨用户检查中基于空命名空间的旧版检查，与替代它的直接
  权限探测一并保留。探测才是真正的检查；保留较弱的那条会虚增计数。
- `bridge/server.py`：`AccessDeniedException` 无论起因都被报告为跨用户或共享写入越界，
  于是 KMS 或配置错误会被叙述为一次越界尝试。应报告实际错误码。
- `infra/test/`：CDK 测试大多是 `JSON.stringify(template).toContain(...)` 子串检查。
  README 中最强的那条论断 —— Runtime 角色对共享记忆不持有任何写 action —— 没有任何
  测试覆盖。应为其补充断言，并同时覆盖：任何 `bedrock-agentcore:` action 上不得出现
  `Resource: "*"`、两张 DynamoDB 表的 KMS 加密，以及部署说明所依赖的 `RETAIN` 移除
  策略。

## 其他值得处理的事项

- **移除 `USER_PASSWORD_AUTH`。** `infra/lib/memory-governance-stack.ts` 同时启用了
  `userPassword` 与 `userSrp`。仅 SRP 即已足够，密码流是不必要的攻击面。bridge 使用
  密码认证已被记为 POC 差距；改用带 PKCE 的授权码流可彻底消除对该流的需求。
- **重新考虑证据桶的 deny 语句。** 该策略使用 `NotPrincipal` 搭配
  `AccountRootPrincipal`。AWS 指引对此模式推荐使用 `aws:PrincipalArn` 上的
  `ArnNotEquals`；当前写法豁免的范围超出预期。真正提供不可变性的机制是第 1 项中的
  版本固定引用，桶策略不应被描述得像是它在提供该保证。
- **校验 bridge 的 `session_key`。** 它由客户端提供，且未经校验即进入摘要策略的
  `{sessionId}` 命名空间模板。检索条件把爆炸半径限制在调用方自己的子树内，但"没有任何
  工具接受 namespace 参数"这一说法仅在参数名层面成立。
- **约束审核 API 的候选项列举。** 目前使用 Scan；候选量增长后改用 status GSI 是已记录
  的后续项。
- **按写入路径拆分共享记忆。** 人工撰写的流程性知识与 LLM 抽取的团队事实是不同的治理
  对象，可能需要不同的闸门。Anthropic 将 `CLAUDE.md` 记录为纳入版本控制的流程性记忆，
  与智能体自写记忆并行运作；Thomson Reuters 描述了把已验证方法提升为可审阅的
  `SKILL.md`、卡在知识管理员控制的审批之后并做版本化
  （[Thomson Reuters](https://blogs.thomsonreuters.com/legal-blog/fiduciary-standards-for-legal-agentic-memory-systems/)）。
  `skills/` 目录已代表该去向，但这一区分尚未在 `docs/architecture.md` 中表述为显式的
  治理边界。

## 定位说明

共享作用域原语在生态中普遍存在 —— group graph、共享记忆块、多 scope 标签、命名空间
元组 —— 但它们放宽的是读写作用域，而非对写入设闸。托管产品提供的是事后策展，例如记忆
CRUD 界面与删除 API，用于在坏记录落库之后加以修正。截至 2026 年 7 月，在所调研的产品
中，未发现将自动化的事前闸门、人工审批与 IAM 强制隔离组合为原生能力的实现。

这一缺位正被独立地指出：一篇从计算机体系结构视角讨论多智能体记忆的文章，将缺失的
*agent memory access protocol*（定义读写语义、权限、作用域与粒度）列为两块缺位协议
之一（[SIGARCH](https://www.sigarch.org/multi-agent-memory-from-a-computer-architecture-perspective-visions-and-challenges-ahead/)）；
而上述 Thomson Reuters 的主张，是从职业责任而非平台能力的论证出发，抵达了"审批闸门 +
版本化的流程性记忆"这一相同结论。

这是用于确定优先级的背景，而非新颖性主张：真正的贡献是治理模型本身，而第 1 至 4 项
决定了它在被对抗性阅读（而非配合性阅读）时是否依然成立。
