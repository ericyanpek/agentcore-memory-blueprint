## 蓝图中采纳的做法

| 示例中的结论 | 蓝图的决策 |

直接创建记录是对原始设计最大的一处修正。旧流程是：批准 -> `CreateEvent` -> 异步语义
抽取。这会让第二个模型有机会改写已批准的内容，并推迟可用时间。新流程是：批准 ->
直接写入长期记录，既确定性又可审计。

## 借鉴而非照搬

### 个人对话集成

[Runtime 集成示例](https://github.com/awslabs/agentcore-samples/tree/ff11ccbb89d391a7c2478160a1b66c63f0b63e59/01-features/04-manage-context-of-your-agent/memory/03-integrations/01-runtime-integration)
使用 Strands 的 `AgentCoreMemorySessionManager`，通过生命周期钩子回灌最近的对话回合
并持久化新消息。当演示 Agent 基于 Strands 时应采用这种方式。`TurnRecorder` 则保持为
一个与框架无关的适配器，用于承载脱敏后的治理事件，同时作为缺少这类钩子的运行时的
兜底方案；切勿为同一个回合同时启用两个写入方。

### 身份

在受信任的服务端模式下，Cognito 的 `sub` 是稳定的个人 actor 标识。
[联邦身份示例](https://github.com/awslabs/agentcore-samples/tree/ff11ccbb89d391a7c2478160a1b66c63f0b63e59/01-features/04-manage-context-of-your-agent/memory/05-security/02-cognito-federated-identity)
改用 Cognito Identity Pool 的 `identityId`，因为 IAM 策略变量绑定的是那个身份。这是
两种不同的模式，而不是两条可以互换的 ID 规则。

### Guardrails 与抽取

[Guardrails 示例](https://github.com/awslabs/agentcore-samples/tree/ff11ccbb89d391a7c2478160a1b66c63f0b63e59/01-features/04-manage-context-of-your-agent/memory/03-integrations/03-guardrails-integration)
只过滤模型输出，并明确提示这并不保护存储环节。生产级 Agent 必须在写入记忆之前评估
输入，并在注入 prompt 之前评估召回的内容。对于那些可以留在短期记忆、但不得成为个人
长期记录的工具、系统、调试、导入或敏感回合，`extractionMode="SKIP"` 是恰当的选择。

### Memory Browser

[Memory Browser 示例](https://github.com/awslabs/agentcore-samples/tree/ff11ccbb89d391a7c2478160a1b66c63f0b63e59/01-features/04-manage-context-of-your-agent/memory/03-integrations/04-memory-browser)
是一个不错的本地只读诊断起点。它接受 Memory ID、actor ID 和 session ID；展示短期事件
和重建后的对话回合；从已配置的策略中发现长期记忆的命名空间模板；并从选定的命名空间
中检索记录。

但它不是一个治理控制台：

- 一次只能配置一个 Memory 资源，而本蓝图刻意把个人记忆与共享记忆拆成两个独立的
  Memory 资源；
- 命名空间发现依赖策略，因此没有配置策略的共享记忆必须手动输入其精确命名空间；
- 长期记忆的浏览走的是语义检索加一个近似通配的查询，而不是分页式的清单视图；
- 不渲染记录元数据、策略 ID、候选 ID、证据链接和评估状态；
- 新增、删除和通用搜索接口都只是占位实现；
- 没有候选队列、Step Functions 执行视图，也没有批准/拒绝流程；
- FastAPI 后端使用运维人员本地的 AWS 凭证，既无用户认证也无项目授权。绑定到
  localhost 能限制暴露面，但并不能让它适用于多用户部署。

对本 POC 而言，可以复用其事件/回合渲染和命名空间模板解析逻辑，但要把单一的自由配置
替换为明确区分的个人资源视图和共享资源视图。浏览与语义检索必须是两个独立操作。共享
视图应展示记录 ID、索引化元数据、候选/证据引用以及评估状态；评估视图应读取候选表，
并复用现有的受 Cognito 保护的决策 API。生产部署还需要经过认证的运维角色、按项目收敛
的授权、审计日志，以及一套独立的、带传播能力的破窗（break-glass）删除流程。

## 暂缓的生产扩展

| 模式 | 暂缓原因 |
|---|---|
| 向 Kinesis 推送 `METADATA_ONLY` 记录流 | 对提升流水线、复制和分析很有价值，但会带来额外成本、IAM/KMS 暴露面、至少一次投递的消费方以及流告警的运维负担。 |
| 跨区域复制 | 需要明确的 RTO/RPO 与数据驻留设计。短期记忆（STM）需要受控的双写；长期记忆（LTM）需要幂等的记录复制。 |
| 完整的 Memory Browser | 对运维和删除流程有用，但需要独立的运维人员授权与隐私控制。 |
| 自管抽取策略 | 如果候选生成本身要迁入 AgentCore Memory，这会很有价值。当前基于 EventBridge 的提案契约更容易讲清楚，而且能让评估策略与抽取内部实现解耦。 |

## 上生产前的运维缺口

- 从 `src/requirements.txt` 打包 `boto3>=1.43.36`。本地的 `boto3 1.42.94` 虽然支持批量
  创建，但其服务模型会拒绝记录的 `metadata` 字段；依赖 Lambda 运行时自带的 SDK 是
  不安全的。
- 在 `AWS/Bedrock-AgentCore` 命名空间下为数据面错误和延迟添加 CloudWatch 告警。
  如果启用了流式推送，还需针对 `StreamPublishingFailure` 和 `StreamUserError` 告警。
- 启用并保护 `/aws/bedrock-agentcore/memory/<memoryId>` 下的摄取日志。
- 为写入失败的个人记忆增加持久化缓冲。检索可以降级为无记忆，但写入丢失绝不能悄无
  声息。
- 增加跨 Memory、审计数据、日志、Knowledge Base 文档和 Skills 的删除传播与保留期
  测试。
