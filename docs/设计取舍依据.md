# 设计取舍依据

> 本文档为主版本。English: [design-rationale.md](design-rationale.md)。
> 相关：[架构设计](架构设计.md) · [下一步演进](下一步演进.md)

本文记录本蓝图四个具体设计选择的理由，以及支持或反驳每一项的外部证据。写法力求可被
反驳：每条论断都标注来源，无法核实的内容明确标记。

本蓝图的设计先于这些证据的收集。本文的目的是说明哪些设计决策经得起外部检验，哪些只是
尚未被挑战过的惯例。

## 一、逐字发布，而非二次抽取

**选择。** 审核通过后，`BatchCreateMemoryRecords` 原样存入已审核的陈述
（`src/blueprint/memory.py`），不经任何抽取模型改写。审核员看到的文本与入库记录逐字节
一致。

最初的动机是可审计性：如果第二个模型对已批准的陈述做了转述，那么审核员实际批准的并非
入库内容，审计链就从事实退化为主张。

**性能层面的独立支持。** 一项 3×3 因子实验（ICLR 2026）交叉比较三种写入策略 —— 原始
分块、mem0 式抽取、MemGPT 式摘要 —— 与三种检索方法，结论是检索方法主导：跨检索方法的
平均准确率相差 20 个点（57.1% 至 77.2%），而跨写入策略仅相差 3–8 个点；其中**零 LLM
调用的原始分块存储**打平甚至优于有损的替代方案
（[arXiv:2603.02473](https://arxiv.org/abs/2603.02473)，代码见
[memory-probe](https://github.com/boqiny/memory-probe)）。该论文的失效分析还指出，多数
性能崩塌发生在检索阶段而非利用阶段。

该论文自陈的局限决定了结论的外推边界：单一 backbone 模型、单一 benchmark、固定检索预算、
以基于提示词的复现替代完整的学习型记忆系统，且正确性判定依赖 LLM 评判器。论文明确指出
原始分块的优势**在上下文预算更紧时可能缩小** —— 这与本文第二节及
[下一步演进](下一步演进.md)第 6 项记录的预算依赖性是同一件事。

**同方向的市场证据。** mem0 在 2026 年的算法修订中，将 `UPDATE` 与 `DELETE` 从写入路径
移除，改为单次追加，把矛盾处理推迟到排序阶段
（[mem0 memory evaluation 文档](https://docs.mem0.ai/core-concepts/memory-evaluation)）。
一个以写入期裁决为差异化卖点的产品，主动从写入期裁决撤退。

**反向证据。** 纯追加存储在长周期内会累积低价值记录，至少一项研究报告检索质量在数周
使用后衰减，而学习型写入策略保持得更好
（[arXiv:2606.21144](https://arxiv.org/html/2606.21144)）。本蓝图采取的调和方式是：
**在准入处设闸，不改写表述。** 政策闸门与人工审核控制一条陈述**是否**被接纳；两者都不
改变它**如何**措辞。

## 二、确定性的检索优先级

**选择。** `docs/architecture.md` 固定了一个全序：实时数据与工具结果，其次是 Git 中的
Skills 与配置，其次是 Knowledge Base 文档，其次是已批准的共享记忆，其次是个人偏好，
最后是模型推断。上层覆盖下层。记忆永远不能覆盖当前数据。

**为何这比看上去更重要。** 三种已被记录的失效模式，使无序的上下文拼装不只是次优，而是
有害：

- **位置敏感性。** 处于上下文中段的证据，被正确取用的可靠性显著低于处于两端的证据
  （[Liu et al., TACL 2024](https://arxiv.org/abs/2307.03172)）。
- **干扰项相似性。** 当干扰项与答案语义接近时，长上下文的性能衰减更严重 —— 而这正是
  已填充的记忆库的固有特征，因为记忆被检索出来的原因**就是**它相似。
- **经验跟随（experience following）。** 智能体会复现它所检索到内容的质量。一个含有
  陈旧或被投毒记录的存储，会产出忠实反映该记录的输出。

优先级规则把"哪些记忆相关"转换为"哪种权威胜出"，而后一个问题有确定答案，前一个没有。

**当前留白之处。** 优先级排的是**层**，并未限定**量**。`src/agent/context_builder.py`
没有上下文预算概念。保留与整合之间的权衡取决于预算，且存在实测的交叉点 —— 预算宽松时
保留策略表现良好，预算紧张时急剧退化
（[arXiv:2607.17545](https://arxiv.org/html/2607.17545v1)）。见
[下一步演进](下一步演进.md)第 6 项。

## 三、人工审核作为反投毒控制

**选择。** 从智能体或桌面客户端到共享 Memory 资源不存在任何通路。只有发布器 Lambda
持有 `bedrock-agentcore:BatchCreateMemoryRecords`，且仅由审核工作流的批准分支调用。

**这针对的是已被验证的攻击类别，而非假想风险。**

- **MINJA** 仅通过普通查询即可将恶意记录注入智能体的记忆库，无需对存储的任何特权访问。
  该论文报告了很高的注入成功率与下游攻击成功率，并发现包括护栏模型、embedding 消毒和
  基于提示词的检测在内的常规防御，都无法可靠阻止它
  （[arXiv:2503.03704](https://arxiv.org/abs/2503.03704)，NeurIPS 2025）。
- **已公开讨论的事件。** 包括 SpAIware、LayerX 的 "Tainted Memories"（写入 ChatGPT
  Atlas 记忆），以及 Radware 的 "ZombieAgent"。与本蓝图最直接相关的是
  **MemoryTrap** —— 针对 Claude Code 被报告并已修复，其中单个被投毒的记忆对象跨会话、
  跨用户、跨子智能体扩散
  （[Help Net Security，2026-04-14](https://www.helpnetsecurity.com/2026/04/14/idan-habler-cisco-agentic-ai-memory-attacks/)）。

由于本蓝图的桌面集成正是关于 Claude Code 与 Codex CLI 共用一套云端记忆，MemoryTrap
就是"对共享写入路径设闸而非信赖客户端行为"这一决定的直接依据。

**范围限制，需精确表述。** 审核仅覆盖**共享层**。个人长期记忆由 AgentCore 自身的抽取
写入，无审核环节；短期事件为直接写入。被投毒的个人偏好会被 IAM 限制在单个 actor 内，
但它未经审核。这是刻意划定的边界而非疏漏 —— 逐条审核个人偏好会使系统无法使用 —— 但
不应将其描述为"记忆已经过审核"。

## 四、两个 Memory 资源而非一个

**选择。** `PersonalMemory` 与 `SharedProjectMemory` 是两个独立资源，因此两者之间的
边界可以在 IAM 策略中表达为资源 ARN，而不是由应用代码校验的命名空间约定。

**AWS 自身的指引支持以命名空间与 IAM 作为 AgentCore Memory 的主要隔离机制**
（[Organizing agents' memory at scale](https://aws.amazon.com/blogs/machine-learning/organizing-agents-memory-at-scale-namespace-design-patterns-in-agentcore-memory/)）。
本蓝图进一步分离了资源，使"桌面角色无法写入共享记忆"成为一条关于该角色**对某个资源
不具备任何 action** 的陈述，而不是一条关于**字符串比较必须处处正确**的陈述。

**这并未换来什么。** 资源分离保护的是共享层，它并不隔离个人资源内部的用户彼此。后者
需要 `poc/validate_identity_pool.py` 中已验证的 per-actor IAM 条件，而 Runtime 角色
目前不具备。见 `docs/architecture.md` 与 README 的适用范围与限制一节；roadmap 中
尚无对应条目。

## 五、关于评估记忆质量

本蓝图验证的是**治理属性**（隔离成立、闸门拦截、令牌不可重放）。它并未宣称记忆提升了
回答质量，也不应通过引用通行 benchmark 数字来开始这样宣称。

已发表的记忆类 benchmark 存在已被记录的方法论问题：

- **LoCoMo。** 一项独立审计报告在 1,540 道题中发现 99 处足以影响打分的答案键错误
  （6.4%），使诚实上限接近 93–94% 而非 100%；同一审计发现其 `gpt-4o-mini` 评判器接受了
  62.81% 的故意错误但主题相邻的答案，其中含糊作答的通过率远高于具体事实性错误
  （[审计](https://penfieldlabs.substack.com/p/we-audited-locomo-64-of-the-answer)、
  [数据](https://github.com/dial481/locomo-audit)）。作为标尺：Northcutt 等
  （NeurIPS 2021）发现十个主流 benchmark 平均约 3.3% 的标签错误已足以扰乱排名。
- **LongMemEval-S。** 每道题的语料都能完整放入当前前沿模型的上下文窗口，这使它更接近
  上下文窗口测试而非记忆测试
  （[同一来源](https://penfieldlabs.substack.com/p/proposal-a-new-benchmark-for-long)）。
- **厂商数字互相存疑。** 对竞品分数的公开复现结果，在两个方向上都与原始数字差距显著
  （[getzep/zep-papers#5](https://github.com/getzep/zep-papers/issues/5)）。

若本蓝图后续要测质量，站得住的方案是：以任务级成功率而非召回率为指标，设置 verbatim
RAG 基线与随机检索对照，并披露 embedding 模型与写入路径成本。分别对抽取、更新和 QA
打分的 benchmark（如 HaluMem，[arXiv:2511.03506](https://arxiv.org/abs/2511.03506)）
比单一聚合数字更具诊断价值，因为它能定位错误的产生环节。

## 六、长上下文并未消除这一需求

大上下文窗口削弱的是检索式记忆的**token 成本**论据，并未削弱其**治理**论据。长上下文
无法提供跨会话持久性、per-record 的权威归属，也无法提供把一条陈述关联到批准人与证据的
审计链。提示词缓存降低成本，但不解决位置敏感性与干扰项相似性，因为被缓存的长上下文
仍然是长上下文。

因此本设计的持久理由是**可审计、受治理的跨会话权威**，而非 token 经济性。这一表述能
经受下一次上下文窗口容量提升。

## 未核实与开放项

- AgentCore 的托管 consolidation 是否存在**未文档化的**取代行为，超出记忆记录流式
  文档中提及的去重与取代范围。该行为未以契约形式规定，故本蓝图不依赖它。
- 关于"注入记录数量增加一个数量级会显著降低准确率"这一被广泛引用的说法，本次核查仅
  追溯到二手来源，因此仅作方向性参考，不作为论据支撑。
