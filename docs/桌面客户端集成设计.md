# 桌面客户端集成 AgentCore Memory：设计与实测

> 本文所有结论均来自对真实 AWS 的实测，非文档推演。
> 原始结果：`build/identity-pool-validation.json`（8 项）、`build/bridge-validation.json`（17 项）。
> 相关：[实验报告](实验报告.md) · [架构设计](架构设计.md) · [演示手册](演示手册.md)

## 一、要解决的问题

Agent 运行在 AgentCore Runtime 内时，调用身份由受信的服务端组件提供。

桌面客户端路径缺少这一前提。工程师分别使用 Claude Code 或 Codex CLI 等本地 Agent，
同时需要共用**同一套云端 AgentCore Memory**：个人偏好按用户隔离，团队经验对成员共享。

身份要求如下：

> **云端凭什么相信"我是谁"？**

如果客户端自己声明身份，那么改一个环境变量就能读同事的个人记忆。本项目最初的单机版 MCP server 恰好就是这个反模式：

```json
"agentcore-memory": { "env": { "AGENTCORE_DEFAULT_ACTOR": "yabolin" } }
```

单人本地使用无妨；一旦多用户共享云端 Memory，这就是一个可越权的漏洞。

## 二、身份约束

**Claude Code 不向 MCP server 或 hook 暴露登录用户的身份。**

Hook 的 stdin 只包含 `session_id`、`cwd`、`transcript_path`、`permission_mode`；MCP server 只能收到你自己配置的 HTTP 头。Claude Code 不会自动附加任何身份断言。

这条约束排除了一整类方案：**任何"由客户端告知服务端我是谁"的设计都不可信**。身份必须来自服务端可独立验签的凭据。

## 三、被排除的方案：Gateway + Cognito 直连

候选方案是使用 AgentCore Gateway。它是托管的 MCP endpoint，支持 CUSTOM_JWT 入站鉴权，
可独立校验 JWT 的签名、issuer 和 audience。

但对交互式 MCP 客户端，这条路走不通，原因有三：

| 缺口 | 后果 |
|---|---|
| Cognito 不支持 RFC 7591 动态客户端注册（DCR） | Claude Code 无法自注册 |
| Cognito 的 OIDC discovery 不在 MCP 客户端期望的路径提供 RFC 8414 元数据 | 元数据发现阶段即失败 |
| Cognito 强制精确 redirect URI 匹配 | 挡掉 MCP 客户端的 loopback 随机端口回调 |

Gateway 确实会按 RFC 9728 返回 `WWW-Authenticate` 挑战，但客户端在后续的元数据发现与 DCR 阶段就断了。AWS 官方博客的示例用的是 Kiro IDE，且需要 `mcp-remote` 代理；公开资料中没有 Claude Code 端到端跑通的案例。

**失败发生在握手阶段，并非 token 过期阶段。**

AgentCore Identity 的 Token Vault 能自动刷新 token，但它解决的是**出站**授权（Agent 调用
GitHub 或 Slack）。Memory 使用 IAM 而非 OAuth，因此 Token Vault 不适用于该路径；
AgentCore Identity 也不充当入站授权服务器。

## 四、采用的方案：本地 bridge + Identity Pool

设计目标是**让 OAuth token 离开热路径**。

```
Claude Code / Codex ──stdio──→ 本地 memory-bridge (MCP server)
                                    │ 1. 用户登录 IdP，拿 id_token
                                    │ 2. Identity Pool 换取带 session tag 的临时凭证
                                    │ 3. 到期前自动静默续期
                                    ▼  （之后全部走 SigV4）
                              AgentCore Memory
                     IAM 按 actorId / namespace 强制隔离
```

桌面端只在首次登录时接触 OAuth；之后所有 Memory 调用都是 SigV4 签名。这绕开了 Claude Code MCP OAuth refresh 的已知脆弱性，也绕开了上一节的三个 RFC 缺口。

### 关键机制：一个 role，靠 session tag 区分人

**不需要给每个用户建 IAM role，也不需要每人一套配置。** 所有工程师共用同一个 role，身份差异体现在 STS 打进凭证的 session tag 上：

```json
{
  "Sid": "OwnShortTermMemoryOnly",
  "Effect": "Allow",
  "Action": [
    "bedrock-agentcore:CreateEvent",
    "bedrock-agentcore:ListEvents",
    "bedrock-agentcore:GetEvent"
  ],
  "Resource": "arn:aws:bedrock-agentcore:...:memory/<personal>",
  "Condition": {
    "StringEquals": {
      "bedrock-agentcore:actorId": "user:${aws:PrincipalTag/userId}"
    }
  }
}
```

Identity Pool 侧的映射（**整个隔离模型的支点**）：

```
PrincipalTags: {'userId': 'sub'}   UseDefaults: False
```

tag 的值来自 IdP 已验签的 `sub` claim，客户端无法影响。100 个工程师 = 1 个 role + 1 份策略；新人加入只需在 IdP 建账号，**AWS 侧零改动**。

### 实测证据：条件键真的强制生效

`bedrock-agentcore` 提供原生 IAM 条件键。用受限凭证实测：

| 条件键 | 实测结果 |
|---|---|
| `bedrock-agentcore:actorId` | 限定 Alice → 读 Alice 成功，读 Bob 被 AWS 拒绝 |
| `bedrock-agentcore:namespace` | 值匹配则允许，不匹配则拒绝 |

关键的**镜像对照**：换 Bob 登录，**同一个 role**，权限完全反转 —— Bob 能读 Bob、被拒读 Alice。这排除了"策略碰巧写死"的可能。两人的 caller ARN 相同：

```
arn:aws:sts::<account-id>:assumed-role/agentcore-memory-desktop-client-role/CognitoIdentityCredentials
```

### 完整策略结构

| Sid | 允许 | 条件 |
|---|---|---|
| `OwnShortTermMemoryOnly` | `CreateEvent`、`ListEvents`、`GetEvent` | `actorId` == 自己 |
| `OwnLongTermMemoryOnly` | `RetrieveMemoryRecords`、`ListMemoryRecords` | `namespace` LIKE `/users/自己/*` |
| `ReadApprovedSharedMemory` | 同上（共享 Memory 资源） | `namespace` == 本项目命名空间（**非通配**） |
| `AppendOwnEvidenceOnly` | `s3:PutObject` | 仅限 `evidence/自己/*` 前缀 |
| `DecryptMemory` | `kms:Decrypt` 等 | — |

注意**没有** `BatchCreateMemoryRecords`。桌面端在 IAM 层面就写不了共享记忆。

## 五、MCP 工具契约：把治理边界编码进工具集合

工具契约不暴露共享记忆直写能力。

| 工具 | 授权来源 | 说明 |
|---|---|---|
| `memory_sign_in` / `memory_sign_out` | — | 建立/清除会话 |
| `memory_whoami` | token | 显示当前身份与权限 |
| `memory_write_turn` | token `sub` | 只能写自己的短期记忆 |
| `memory_search` | token `sub` | 个人偏好与共享知识**分列返回** |
| `memory_capture_evidence` | token `sub` | 落 S3 换取 `s3://` 证据引用 |
| `memory_propose_shared` | token `sub` | 只能**提案**，进人工审核流 |
| `memory_review_queue` / `memory_review_decide` | token + reviewer 组 | 非审核员收到明确 403 |
| ~~`memory_write_shared`~~ | — | **不提供** |

三条设计约束：

1. **没有任何工具接受 `actor_id` 或 `namespace` 参数** —— 客户端无法声明自己是谁。
2. **凭证短期且带 tag** —— 即使 bridge 有 bug，IAM 也拦得住。
3. **没有直写共享记忆的工具** —— 团队知识只能提案。

`memory_search` 刻意把两类知识分列，并附带优先级规则（实时数据 > 权威文档 > 共享知识 > 个人偏好 > 模型推断），避免模型把个人偏好当团队结论。

## 六、证据链：为什么本地 transcript 不算证据

治理规则要求候选必须带 `evidence_ref`，且指向不可变记录（`trace://`、`s3://`、`log://`）。

**Claude Code 的 transcript 在用户自己的磁盘上，可改可删，因此不能作为证据。** 否则审核员批准的是一条事后无法核实的陈述。

解决方式：`memory_capture_evidence` 把对话片段连同 SHA-256 摘要上传到 append-only 审计桶，返回 `s3://` 引用。

桶的约束（CDK 定义）：

- KMS 加密、强制 SSL、阻断公开访问、开启版本控制
- 桶策略 DENY `s3:DeleteObject`、`s3:DeleteObjectVersion`、`s3:PutObjectAcl`（排除账号 root，否则生命周期清理与应急恢复都会被锁死）
- 桌面 role 只有 `s3:PutObject`，且限定自己的前缀
- **`evidence_ref` 固定 `versionId`**

### 初始实现中的错误假设

第一版只 DENY 了删除，因此得出"提案人改不了自己的证据"的结论。代码评审后的实测否定了
这一假设：

```
2. 同一 key 覆盖写入（伪造证据）: *** ALLOWED ***
3. 删除:                          AccessDenied
```

桶策略挡不住作者用**同一个 key 重新 PUT**。版本控制会保留旧版本，但裸 `s3://bucket/key` 引用解析到的是**最新版本** —— 于是提案人可以在获批后把证据替换掉，而审核员点开链接看到的是伪造内容。我最初的测试只测了删除，正好漏掉这条路径。

修法不是禁止覆盖（那会破坏正常重试），而是**让引用指向具体版本**：

```
s3://<bucket>/evidence/user:<sub>/2026/07/28/163727-38dee654ece1.json?versionId=NL0WCbWdQcQEjW5w...
```

覆盖仍然允许，但删除版本被拒，所以被引用的那一份永远不变。实测证明：

```
[PASS] The reviewed evidence version cannot be altered by its author
       pins_version=yes  delete=AccessDenied
       overwrite_key=ALLOWED  delete_pinned=AccessDenied  other_prefix=AccessDenied
```

直接读 S3 对照同一 key 的两个版本：

```
latest=False  NL0WCbWdQcQEjW5w... -> {"captured_at": "2026-07-28T16:37:27...", "pr...
latest=True   rZsO4DeDfN0FslAr... -> {"excerpt":"FORGED"}
```

伪造内容成了 latest，但**引用固定的那个版本仍返回原文**。审核员看到的永远是他当初批准的内容。

提案人也无法往别人的前缀写入伪造证据（`other_prefix=AccessDenied`）。

## 七、提案链路：POST /proposals

桌面端不持有 `events:PutEvents` 权限（否则就能绕过校验直接投事件）。提案改走 Cognito 保护的 API：

```
Claude Code → memory_propose_shared → POST /proposals (Cognito)
                                          │ 校验 + 从 token 取 sub
                                          ▼
                                    EventBridge
                                          ▼
                          Step Functions（政策闸门 → 人工审核）
                                          ▼
                                    共享 Memory
```

`src/handlers/propose_candidate.py` 的两个要点：

**1. proposer 只从 token 取，绝不信 body。** 否则客户端可以把一条被驳回的陈述归到同事名下。

```python
"proposer_actor_id": f"user:{subject}",   # subject 来自 Cognito claims
```

`project_id` 同理，由服务端环境变量决定，body 无法覆盖。

**2. 不谎报状态。** 未通过政策闸门的候选永远不会到审核员面前，所以响应返回 `SUBMITTED` 并附 `eligible_for_review`，而非一律声称 `PENDING_REVIEW`。

这个 Lambda 的 IAM 权限只有 `events:PutEvents` —— 有 CDK 测试断言它碰不到 Memory 和候选表。

## 九、部署与配置

### 团队共享配置（`.mcp.json`，可提交）

```json
{
  "mcpServers": {
    "memory-bridge": {
      "type": "stdio",
      "command": "${CLAUDE_PROJECT_DIR}/bridge/.venv/bin/python",
      "args": ["${CLAUDE_PROJECT_DIR}/bridge/server.py"],
      "env": {
        "MEMORY_BRIDGE_DEPLOYMENT": "${CLAUDE_PROJECT_DIR}/build/poc-deployment.json",
        "MEMORY_BRIDGE_IDENTITY_POOL_ID": "${MEMORY_BRIDGE_IDENTITY_POOL_ID}"
      }
    }
  }
}
```

项目级作用域即"全团队拿到同一个 server 定义，各自认证为自己"。文件中不含任何密钥；`${VAR}` 由各人本地提供。

### 验证命令

```bash
# IAM 隔离（会创建 Identity Pool、共享 role、测试用户）
python3 poc/validate_identity_pool.py --deployment build/poc-deployment.json

# bridge 行为（以两个用户身份驱动真实 MCP 协议）
python3 bridge/validate_bridge.py --python "$PWD/bridge/.venv/bin/python"
```

### 上游 IdP 的选择

本次实测用的是项目已有的 Cognito User Pool。生产环境应沿用公司现有身份源：

| 方案 | 适用 |
|---|---|
| Identity Center | 已用 IdC 管理 AWS 访问，人员生命周期跟随 HR 流程 |
| 企业 IdP 直连（Okta / Entra ID） | 身份源在企业 IdP，不引入 IdC |
| Cognito User Pool | POC / 外部承包商 |

**换 IdP 只替换上游，下游 IAM 部分一行不改** —— 隔离逻辑挂在 session tag 上，不关心 tag 由谁签发。

判断依据很简单：工程师现在怎么登录 AWS，就沿用那条路，不要新造身份源 —— 否则人员离职要记得两处删账号，这是真实的安全债。

## 十、实测方法上的教训

本设计的两轮验证中，**首轮都是"全部通过"，但核对原始证据时各发现了假阳性**：

### 陷阱一：真空通过

"Bob 搜不到 Alice 的内容"这条检查通过了 —— 但当时 Alice 的偏好记录是 **0 条**（异步抽取未完成），双方都是空的。它证明的是数据不存在，而非隔离生效。

**修正**：改为直接测跨用户读取权限，由 AWS 立即返回 AccessDenied，不依赖异步抽取。

这与[实验报告](实验报告.md)第七章记录的是同一类陷阱 —— 说明这个错误极易重犯。

### 陷阱二：测到了错误的失败原因

"低置信度提案被拦"这条通过了 —— 但实际返回的是 403（路由未部署），不是政策拒绝。API Gateway 对未部署路径返回的是措辞误导的 SigV4 错误。

**修正**：拆成两条 —— 本地可确定的校验（未知 category、置信度越界）单独断言；路由缺失的情况诚实报告而非假装成功。

> **方法论**：安全类断言必须同时验证"该拦的拦住了"和"该有的确实有"。只测前者，一个完全空的系统会通过所有隔离测试。
> 同样重要的是：**核对失败的原因码**，而不只看"是否失败"。

## 十一、生产差距

| 差距 | 说明 | 严重度 |
|---|---|---|
| 缺少项目成员授权 | 策略已收紧为单一项目命名空间（不再用 `project:*` 通配），但**项目归属仍是部署期固定的，而非按用户判定**。多项目场景需把项目成员身份放进 IdP claim，映射为独立的 session tag，再在条件中引用 | 高 |
| 项目归属不能用 `cwd` 推断 | 很自然会想从 git remote 或 `cwd` 推断当前项目，但 `cwd` 也是客户端声明的，伪造即可越权。`cwd` 只能作为挑选默认项目的**提示** | 高 |
| 证据仅覆盖显式捕获 | `memory_capture_evidence` 需要 Agent 主动调用。若模型跳过这一步，提案会因 evidence 校验失败而被拒 —— 安全但体验不佳。可考虑用 hook 自动捕获 | 中 |
| Bridge 用密码登录 | POC 用 `USER_PASSWORD_AUTH`。生产应走浏览器授权码流 + PKCE，避免密码经过 MCP 工具参数 | 中 |
| Token 缓存在本地磁盘 | refresh token 存 `~/.agentcore-memory-bridge/session.json`（0600 权限）。生产应使用系统密钥链 | 中 |
| 无 Guardrails | 写入存储前、记忆注入提示词前都应经过 Bedrock Guardrail | 中 |
| 证据桶保留期 365 天 | 需与合规要求对齐；当前无 Object Lock（合规模式），仅靠桶策略 DENY | 中 |
| Hook 集成未实现 | 自动记忆写入/检索需 hook 调用本地 bridge（hook 本身拿不到身份，不应直连云端） | 低 |

## 十二、结论

Claude Code 和 Codex 可通过本地 bridge 与 Identity Pool 接入云端 AgentCore Memory。
该设计以桌面客户端不是可信身份来源为前提。

实现步骤如下：

1. 用户在本地登录企业 IdP
2. Identity Pool 把已验签的 `sub` 映射为 session tag
3. **单个共享 IAM role** 用 `${aws:PrincipalTag/userId}` 强制隔离
4. 工具面不提供越界能力，团队知识只能提案

隔离由 AWS 控制强制执行，不依赖客户端或 bridge 的正确行为。该属性已通过双用户镜像对照
验证。
