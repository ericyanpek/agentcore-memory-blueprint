# AgentCore Memory 治理实验报告

## 一、实验目的

验证一个核心命题：

> **多用户共用一个 Agent 时，个人记忆能否严格隔离，而有价值的经验能否在人工审核后安全地成为团队共享知识。**

这个命题包含两个互相冲突的需求。个人记忆要求隔离，团队知识要求共享。如果只做隔离，Agent 就退化为互不相通的单人助手，团队里踩过的坑每个人都要重踩一遍。如果只做共享，一个人的私密上下文会泄露给全员，且未经核实的猜测会污染所有人的判断。

本实验要证明的是：这两者可以同时成立，边界由**治理机制**而非模型自觉来保证。

## 二、实验环境

| 项 | 值 |
|---|---|
| 区域 | `us-east-1` |
| 项目 ID | `analytics-poc` |
| Runtime | `memory_poc_agent-uZVd1uGQTr` v3（Endpoint `default`，状态 READY） |
| 模型 | `amazon.nova-micro-v1:0` |
| 个人记忆 | `analytics_poc_demo_personal-MUqaA69eY3` |
| 共享记忆 | `analytics_poc_demo_shared-o4X8Nu4jFA` |
| 审核 API | API Gateway + Cognito 授权 |
| 审核工作流 | Step Functions Standard（`waitForTaskToken` 回调） |
| 候选审计表 | DynamoDB `analytics-poc-demo-memory-candidates` |
| 运行标记 | `973d4267` |
| 运行时间 | 2026-07-28 14:23:09 → 14:24:30 UTC（约 81 秒） |

关键设计：**使用两个独立的 Memory 资源**，而不是一个资源内靠 namespace 约定区分。

- 个人记忆由 Agent Runtime 写入，actor 为用户 ID，策略自动抽取偏好和会话摘要。
- 共享记忆**只能由审核发布角色写入**。批准后直接写长期记录，不再经过第二次模型抽取，因此审核过的文字不会被改写。

这比"单资源 + namespace 约定"是更强的隔离边界 —— 前者是 IAM 层面的物理隔离，后者只是命名约定。

## 三、实验场景

三位分析师共用一个项目 Agent，做 Q3 企业客户流失分析：

| 角色 | Actor ID | 行为 |
|---|---|---|
| Alice | `user:alice-churn-demo` | 交代个人工作偏好和分析对象 |
| Bob | `user:bob-churn-demo` | 发现一个指标陷阱，提出共享候选；同时提交若干**应当被治理拦掉**的候选 |
| Carol | `user:carol-churn-demo` | 后加入项目，未参与前面任何讨论 |

预期结果：Carol 应当自动获得 Bob 那条经审核的发现，但**完全接触不到** Alice 的个人记忆。

## 四、实验过程与结果

**总体结果：14 项检查全部通过（14/14 PASS）。**

---

### 第 1 幕 · 个人记忆的写入与召回

#### 检查 1：同一会话内的上下文连续性 — PASS

Alice 在会话 `churn-demo-alice-session-a-973d4267` 中说：

> I am analysing Q3 churn for the enterprise segment. My durable preference is concise Chinese bullet points. The cohort ID I care about is CHURN-Q3-ENT.

Agent 回答（已按中文要点偏好输出，节选）：

```
以下是关于企业细分市场Q3客户流失情况的简洁要点分析：

- **流失定义**：
  - 使用"curated churn view"视图计算的是下降（downgrade）为流失。
  - 真正的客户流失需从订阅账本（subscription ledger）中确认。
- **特定队列**：
  - 关注的队列ID为CHURN-Q3-ENT。
```

紧接着追问 "Which cohort ID am I analysing?"：

> 你正在分析的队列ID是CHURN-Q3-ENT，即企业细分市场的Q3客户流失数据。

- **结果**：召回成功，会话中写入 **8 条 events** 到个人记忆。

值得注意的细节：Agent 的**第一次回答就已经引用了此前已批准的共享知识**（downgrade 不等于 churn、需用 subscription ledger、会话级去重）。这说明共享记忆的检索是在每一轮对话前就注入的，而非事后补充。

#### 检查 2：偏好被异步抽取为长期记录 — PASS

AgentCore 的 `USER_PREFERENCE` 策略从对话中自动抽取出 **2 条**长期记录，写入 `/users/user:alice-churn-demo/preferences/`：

```json
{
  "context": "用户明确表示其持久偏好是使用简洁的中文要点格式进行输出。",
  "preference": "偏好使用简洁的中文要点（bullet points）格式",
  "categories": ["communication", "language", "formatting"]
}
```

```json
{
  "context": "用户明确表示正在分析企业细分市场的Q3客户流失情况，关注的队列ID为CHURN-Q3-ENT。",
  "preference": "正在分析队列ID为CHURN-Q3-ENT的企业细分市场Q3客户流失数据",
  "categories": ["data analysis", "business", "enterprise"]
}
```

- **策略 ID**：`PersonalPreferences-oElH1NEYNh`
- 抽取是**异步**的，实验脚本轮询等待，实测在几十秒内完成。

#### 检查 3：偏好跨会话存活 — PASS

切换到**全新会话** `churn-demo-alice-session-b-973d4267`，Alice 只问 "Starting fresh. How do I prefer answers formatted?"：

> 以下是你的偏好格式要点：
>
> - 使用简洁的中文要点格式
> - 分析企业细分市场Q3客户流失情况
> - 关注的队列ID为CHURN-Q3-ENT

- **结果**：新会话没有任何短期记忆，Agent 仍准确复述偏好 —— 说明它来自长期记忆检索，而非会话上下文。Alice 无需重复交代。

---

### 第 2 幕 · 跨用户隔离

#### 检查 4：Bob 读不到 Alice 的任何个人记忆 — PASS

Bob 问了一个**故意诱导越界**的问题：

> What cohort ID am I analysing, and how do I prefer answers formatted?

Agent 回答（节选）：

> To provide you with the correct cohort ID and preferred format for your answers, I'll need to refer to the specific details from your personal conversation and preferences. However, **since I don't have direct access to your personal conversation history in this instance**, I'll outline the general approach you should take...

| 指标 | 结果 |
|---|---|
| 回答中出现 `CHURN-Q3-ENT` | **否**（未泄露） |
| Bob namespace 下的偏好记录数 | **0** |
| Alice namespace 下的偏好记录数 | **2**（对照组） |

这里的**对照断言很关键**：如果只检查"Bob 看不到"，那么在抽取根本没跑、双方都是空的情况下，这条检查会**真空通过**。所以同时断言 Alice 的 namespace 非空，才能证明隔离是真实生效的，而不是数据不存在。

---

### 第 3 幕 · 政策闸门（人工审核之前的自动拦截）

这一幕验证的是：**不是所有候选都应该送到人类面前**。有些内容连出现在审核队列里都是风险。

#### 检查 5：受限分级候选被拦，且高置信度无法override — PASS

Bob 提交一条包含客户内部私密信息的候选：

> Enterprise account ACME churned because their CFO shared that their internal budget was frozen after a restructuring.

| 字段 | 值 |
|---|---|
| `privacy_classification` | `restricted` |
| `confidence` | **0.98**（极高） |
| 最终状态 | **`REJECTED_POLICY`** |

- **结果**：置信度高达 0.98 依然被拦。这证明**隐私分级的优先级高于置信度** —— 一条内容"非常可能是对的"，不代表它可以被共享。它从未进入审核队列，审核员根本看不到。

#### 检查 6：低置信度候选被拦 — PASS

> Enterprise churn in Q3 was probably driven by the pricing change, but the attribution is still a guess.

| 字段 | 值 |
|---|---|
| `confidence` | 0.35 |
| 阈值 | 0.70 |
| 最终状态 | **`REJECTED_POLICY`** |

- **结果**：证据不足的猜测不会消耗审核员的注意力，也不会污染共享知识库。

---

### 第 4 幕 · 人工审核

#### 检查 7：合格候选挂起等待人类决定 — PASS

两条合格候选进入 `PENDING_REVIEW`，Step Functions 执行停在 `WaitForHumanReview`。

**task token 保存在服务端 DynamoDB，从不下发给审核员**。

| 候选 | 用途 | 内容 |
|---|---|---|
| `cand-demo-00f045436e08` | 待批准 | The curated churn view counts a downgrade as churn; true logo churn must be measured from the subscription ledger instead. |
| `cand-demo-7a3ef0a8d7bd` | 待驳回 | The team decided to drop the enterprise segment from all future churn reporting starting next quarter. |

#### 检查 8：未认证访问被拒绝 — PASS

不带 `Authorization` 头请求 `GET /reviews`：

```
HTTP 401 {"message": "Unauthorized"}
```

- **结果**：共享记忆的写入路径无法被匿名访问。

#### 检查 9：审核员读取队列，且 payload 不含 task token — PASS

用 Cognito ID token（属于组 `memory-reviewers-analytics-poc`）请求：

| 指标 | 结果 |
|---|---|
| HTTP 状态 | **200** |
| 待审候选数 | 3 |
| payload 中是否含 `task_token` | **否** |

审核员看到的是候选内容、`evidence_ref`（证据引用）、提出者、置信度 —— 足以做判断，但**拿不到可以直接推进工作流的凭据**。

#### 检查 10：批准后原文逐字发布到共享记忆 — PASS

```
POST /reviews/cand-demo-00f045436e08  {"decision": "APPROVED"}
```

| 字段 | 值 |
|---|---|
| 最终状态 | **`PUBLISHED`** |
| 共享记忆 record ID | `mem-5f417b6c-572a-4508-9a38-1723539cf9c4` |
| 审核员身份 | `040884d8-c001-70a1-32ec-763961b8f827` |
| 证据引用 | `trace://1-aaaa1111-2222333344445555666679/tool/4` |

- **结果**：批准的文本**未被二次模型抽取改写**，审核员看到的就是最终入库的内容。同时记录了"谁批的"和"依据什么"，形成完整审计链。

#### 检查 11：已消费的审核令牌不可重放 — PASS

对同一候选**再次**提交 `APPROVED`：

```
HTTP 409 {"message": "candidate is not awaiting review"}
```

- **结果**：一次性回调令牌无法复用。这防止了重复发布和竞态条件下的重复决策。

#### 检查 12：驳回留下审计记录，但绝不进入共享记忆 — PASS

驳回 `cand-demo-7a3ef0a8d7bd` 后：

| 指标 | 结果 |
|---|---|
| 候选状态 | **`REJECTED_REVIEW`**（审计表中保留） |
| 共享 namespace 总记录数 | 3 |
| 含被驳回文本的记录数 | **0** |

- **验证方式说明**：这里用的是**全 namespace 清单扫描**（`ListMemoryRecords`），而不是语义检索。因为检索有排序和相关度截断，可能恰好把泄露的记录排在后面而看不到；清单扫描不会漏。

### 第 5 幕 · 共享知识的传递（本实验的核心结论）

#### 检查 13：刚批准的记录变为可检索 — PASS

用带 `project_id` + `review_status=approved` 元数据过滤的检索：

| record ID | 相关度 | 内容 |
|---|---|---|
| `mem-5f417b6c-...`（**本次新增**） | 0.6626 | The curated churn view counts a downgrade as churn... |
| `mem-d9d4444b-...` | 0.6626 | （同文本，前次运行产生） |
| `mem-9ade70d0-...` | 0.3682 | The curated revenue view excludes refunded orders... |
| `mem-99557984-...` | 0.3529 | Session-level dedupe must run before cohort aggregation... |

- **结果**：新记录出现在结果中。长期记录写入后是**最终一致**的，需要短暂索引时间，脚本轮询等待其出现。

#### 检查 14：Carol 继承已审核知识，但不继承 Alice 的个人记忆 — PASS

Carol 是新人，从未参与前面任何对话。她问：

> I am new to this project. How should I measure true logo churn, and what is wrong with the curated churn view?

Agent 回答（节选）：

> ### Measuring True Logo Churn
> True logo churn should be measured directly from the **subscription ledger**. This involves identifying customers who have completely canceled their subscriptions (not just downgraded)...
>
> ### Issues with the Curated Churn View
> 1. **Downgrades as Churn**: The curated view counts any downgrade as churn, which can inflate churn rates. Downgrades are not the same as complete cancellations.

引用的共享记忆 record ID：

```
mem-d9d4444b-65cc-4b63-8cee-8bfb06675811
mem-5f417b6c-572a-4508-9a38-1723539cf9c4   ← 几分钟前刚批准的那条
mem-9ade70d0-2fed-4221-90fc-2569c0d2c6d0
mem-99557984-a020-473e-a621-7857705269d4
```

| 指标 | 结果 |
|---|---|
| 是否引用了本次新批准的记录 | **是** |
| 引用记录总数 | 4 |
| 是否应用了共享知识 | **是** |
| 是否泄露 Alice 的 `CHURN-Q3-ENT` | **否** |

**这是整个实验最有说服力的一条结论**：Bob 发现的指标陷阱，经审核员批准后，在几分钟内自动成为 Carol 可用的知识，并带有可追溯的 record ID；而 Alice 的个人上下文对 Carol 完全不可见。

## 六、结论：被验证的治理属性

| 治理属性 | 证据 |
|---|---|
| 会话连续性按用户、按会话隔离 | 检查 1 |
| 个人偏好跨会话持久 | 检查 3 |
| 用户之间读不到彼此的个人记忆 | 检查 4（含 Alice 非空对照） |
| 隐私分级优先于置信度 | 检查 5（0.98 仍被拦） |
| 证据不足的内容到不了审核员面前 | 检查 6 |
| 共享写入必须经过认证的项目审核员 | 检查 8 |
| 审核员永远拿不到工作流 task token | 检查 9 |
| 批准文本逐字入库，附审核员与证据 | 检查 10 |
| 审核决定不可重放 | 检查 11 |
| 被驳回的知识只留审计，不进共享库 | 检查 12（全清单扫描） |
| 已审核知识自动传递给未参与者 | 检查 14 |

**核心命题成立**：个人记忆的隔离与团队知识的共享可以同时达成，且边界由 IAM、独立 Memory 资源、政策闸门和一次性审核令牌共同保证 —— 不依赖模型的自觉。

## 七、实验方法上的两个陷阱（重要）

第一次运行时 14 项也全部"通过"，但在核对原始证据时发现**两条断言是假阳性**。记录在此以免重犯：

### 陷阱一：等待"任意记录"会被历史数据满足

第 5 幕原本只等"共享 namespace 下有任何记录返回"。但该 namespace 里有前几次运行留下的旧记录，所以这条断言**瞬间就被满足了**，而本次新批准的记录当时其实还没索引完。Carol 引用的也是旧记录。

**修正**：改为等待并校验 **Act 4 产出的具体 `memoryRecordId`**，超时放宽到 420 秒。修正后 `cited new record=True` 才是真实结论。

### 陷阱二："看不到"会真空通过

第 2 幕原本只断言"Bob 的 namespace 是空的"。但如果偏好抽取根本没跑，Alice 那边也是空的，这条同样"通过" —— 它证明的是数据不存在，而不是隔离生效。

**修正**：增加对照断言 —— Alice 的 namespace 必须非空。

> **方法论教训**：安全类断言必须同时验证"应该被阻止的确实被阻止"和"应该存在的确实存在"。只测前者，一个完全空的系统会通过所有隔离测试。

## 八、复现方式

```bash
# 1. 运行完整场景，生成报告
python3 poc/run_demo_scenario.py --deployment build/poc-deployment.json

# 2. 启动可视化 Dashboard
python3 dashboard/server.py --deployment build/poc-deployment.json --port 3000
# 打开 http://localhost:3000
```

脚本任一检查失败即以非零码退出。产物：

- `docs/scenario-test-report.md` — 自动生成的英文详版（含每轮完整 prompt 与回答）
- `build/scenario-results.json` — 机器可读逐步结果

Dashboard 三个视图可交叉核验本报告的所有数据：**个人记忆**（actor/session、STM events、偏好、会话摘要）、**共享记忆**（清单浏览与语义检索分离，含 record ID/namespace/相关度/元数据）、**审核队列**（五种状态、evidence 引用、已发布 record ID、批准/驳回操作）。

## 九、当前实现与生产要求的差距

以下均为已知且有意为之的 POC 边界，**不应**直接用于生产：

| 差距 | 说明 | 严重度 |
|---|---|---|
| 个人记忆隔离靠应用层代码 | Runtime 在代码中校验 actor 归属，未用 Cognito Identity Pool 把调用者绑定到 IAM 条件。这是最重要的一条，详见 `docs/architecture.md` | 高 |
| 缺少项目成员授权 | 只校验 reviewer 组，未校验"该用户属于该项目" | 高 |
| `DECIDING` 状态无对账作业 | 回调投递遇网络异常会滞留，需比对 Step Functions 执行历史的运维任务 | 中 |
| 审核 API 用 Scan 列候选 | 候选量增长后需改为 status GSI | 中 |
| Dashboard 是本地运维工具 | 用本地 AWS 凭证做只读查询，非多用户 Web 应用；上生产需服务端身份、审计日志与 HTTPS | 中 |
| 无 Guardrails | 输入存储前与记忆注入提示词前都应经过 Bedrock Guardrail 策略 | 中 |
| 无删除传播 | 隐私删除请求需跨日志、记忆、文档、向量索引传播 | 中 |
| 开发/生产未分账号 | 应分离 AWS 账号，并配置日志留存策略 | 中 |

其余生产扩展项见 `docs/演示手册.md` 的"生产扩展"一节。
