# AgentCore Memory 与业内记忆产品横评

> 本文档为主版本。English: [memory-landscape.md](memory-landscape.md)。
> 相关：[设计取舍依据](设计取舍依据.md) · [下一步演进](下一步演进.md)

本文回答两个问题：AgentCore Memory 与业内记忆产品的能力边界差在哪；本蓝图叠加在
AgentCore 上产生了什么放大效应。写法与本仓库其余文档一致：结论标注一手来源，AgentCore
的短板与竞品的长处如实写出，无法核实的内容明确标记。

核对时间 2026-07-29。产品能力变动快，引用前请复核。

## 一、能力对照

| | 检索 | 失效/取代语义 | 共享作用域 | 写入是否设闸 | 隔离强制层 |
|---|---|---|---|---|---|
| **AgentCore Memory** | 纯语义（余弦），**10 个元数据操作符 + 预过滤** | **无**（取代走删除路径） | namespace 约定 | 否 | **IAM 条件键** |
| **mem0** | **hybrid：语义 + BM25 + 实体匹配** | 自动路径 ADD-only；显式 update/delete 需自行调用 | `user_id`/`agent_id`/`run_id` + `org_id` | 否 | 应用层参数 |
| **Zep / Graphiti** | 语义 + BM25 + 图遍历 | **Fact Invalidation：失效时刻记录在边上** | 独立 Graph（非 User Graph） | 否 | 应用层 |
| **Letta** | 语义 | 版本化 block | `shared_block_ids`；一个 agent 改，其余**立即可见** | 否（有只读 block 标志） | 应用层 |
| **Vertex Memory Bank** | 语义 | consolidation 含矛盾消解 | scope 可覆写 | 否（但有**预抽取钩子**） | 应用层 |
| **Databricks** | 语义 | — | scope + Unity Catalog | 否（事后 CRUD） | UC ACL |
| **Foundry Agent Memory** | 语义 | TTL + 逐条 CRUD | scope | 否（事后策展） | 应用层 |

### AgentCore 明确不如竞品的地方

**1. 检索只有语义,没有关键词与 hybrid。** `RetrieveMemoryRecords` 文档明确写
"performs a semantic search",分值"is derived from the cosine similarity of embedding
vectors"。API 面没有任何 BM25、hybrid 融合或重排参数,embedding 模型也不暴露给用户
（可选的是**抽取/合并所用的推理模型**,与检索 embedding 不是一回事）。

这条差距有量化意义：ICLR 2026 一项 3×3 因子实验显示**检索方法拉动准确率 20 个点
（57.1% → 77.2%），远超写入策略的 3–8 个点**
（[arXiv:2603.02473](https://arxiv.org/abs/2603.02473)）。mem0 的 2026 重写恰好走了
相反方向：写入退回 ADD-only，检索升级为 hybrid。**在纯检索质量这一维，mem0 与 Zep 的
配置强于 AgentCore，且这不是使用方式问题，是产品能力边界。**

对照之下，同属 AgentCore 家族的 **Registry** 宣传"hybrid semantic and keyword search"，
Memory 没有 —— 说明这是有意的功能划分，而非疏漏。

**2. 没有失效语义 —— 而且 AWS 自己的文档互相矛盾。**

AWS 机器学习博客称 consolidation 会"把过时记忆标记为 **INVALID** 而非立即删除，从而维持
不可变审计线索"
（[deep dive 博客](https://aws.amazon.com/blogs/machine-learning/building-smarter-ai-agents-agentcore-long-term-memory-deep-dive/)）。
但 API 参考中的 `MemoryRecord` 只有 `content`、`createdAt`、`memoryRecordId`、
`memoryStrategyId`、`namespaces`、`metadata` 六个成员，**没有任何状态或有效性字段**；
记忆记录流式只定义三种事件（`MemoryRecordCreated`/`MemoryRecordUpdated`/
`MemoryRecordDeleted`），且把 consolidation 的取代归入**删除**路径。

> `MemoryRecordOutput` 上确有 `MemoryRecordStatus`，但它是批量写操作的返回状态
> （SUCCEEDED/FAILED），**不是记录生命周期状态**，不可引为失效依据。

**结论：客户可见的 INVALID 状态不存在。** 需要审计线索就得自己保留（候选表 + Kinesis
流式落数据湖）。相比之下 Zep 的 Fact Invalidation 是产品化能力：新数据推翻旧事实时，
失效时刻被写在该事实的边上，Context Block 会带上事实的生效与失效日期。**这是 Zep 明确
领先 AgentCore 的一项。**

### AgentCore 明确领先的地方

**1. 隔离由平台强制，不靠应用自律 —— 这是最实质的差别。**

`bedrock-agentcore:actorId` 与 `bedrock-agentcore:namespace`/`namespacePath` 是真实的
IAM 条件键，可与 `${aws:PrincipalTag/userId}` 组合。其余产品的 scope 都是**函数参数或
数据库列**：写对了就隔离，写错了就泄露。

差别不是理论上的。Databricks 的文档把这条限制说得最诚实：
> "Scope is the isolation boundary between users. **Configure the scope in trusted
> code, and never let the model set it. The app service principal can read every
> scope.**"
（[Databricks managed agent memory](https://learn.microsoft.com/en-us/azure/databricks/agents/agent-memory/managed-memory)）

"never let the model set it" 是把安全责任交还给应用；"service principal 能读所有 scope"
是承认平台侧不存在 per-user 边界。而在 AgentCore 上，同样的编码错误会被 IAM 拒绝，因为
条件在 AWS 侧判定。

**同类事故已经发生过。** mem0 的**自托管 `openmemory/api` 组件**被登记
CVE-2026-59705 / EUVD-2026-42126（CWE-306，CVSS 9.3）：路由注册时未挂鉴权中间件，
未授权攻击者可传入任意 `user_id` 读写删除他人记忆，或以 `global_pause=true` 造成全员
拒绝服务
（[ENISA](https://euvd.enisa.europa.eu/vulnerability/EUVD-2026-42126) ·
[GitHub Advisory](https://github.com/advisories/GHSA-xgj7-grxr-prrp)）。

> **范围必须说准**：所有权威来源指向的都只是**可自托管的 OpenMemory API 组件**，
> **没有任何公告牵涉 mem0 托管平台**。这不是"mem0 有严重 CVE"，而是"自托管组件的鉴权
> 缺失"。同类还有 CVE-2026-31240 / 31241。此外 mem0 提供 PII 过滤自定义指令与置信度
> 阈值等可选摄入控制，评价时应一并计入。

这个案例的价值不在于指摘竞品，而在于说明**结构差异**：当 scope 只是应用层参数时，一处
中间件遗漏就等于全量越权；当边界是 IAM 条件时，同样的遗漏被平台挡下。

**2. 预过滤架构 —— 被低估的一项。**

devguide 明确写：
> "**Metadata filters are applied before the vector similarity search runs
> (pre-filtering). This reduces the candidate set first. As a result, the K-nearest
> neighbor (KNN) search operates on a smaller, more relevant subset.**"
（[metadata 过滤文档](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/long-term-memory-metadata.html)）

配合 10 个操作符（`EQUALS_TO`、`EXISTS`、`NOT_EXISTS`、`BEFORE`、`AFTER`、`CONTAINS`、
`GREATER_THAN`、`GREATER_THAN_OR_EQUALS`、`LESS_THAN`、`LESS_THAN_OR_EQUALS`，
botocore 1.43.58），这意味着**治理条件可以进入检索路径本身**，而不是事后筛选。

> **SDK 版本陷阱**：早于 `boto3>=1.43.36` 的版本只暴露前三个操作符。本仓库
> `src/requirements.txt` 已 pin，但用旧 SDK 核对能力会得出错误结论 —— 本文档此前就犯过
> 这个错。

**3. `STRICTLY_CONSISTENT` 元数据。** 允许**应用**直接设定元数据值，不经 LLM 推断
（对比 `LLM_INFERRED`）。这是一个真正的可信写入原语：治理字段不由模型填写。

**4. 托管边界完整。** 无需自建向量库、无需外部 embedding 服务、KMS/VPC/CloudTrail 齐备。
mem0 自托管路线需要 Docker + Qdrant/Postgres + 外部 embedding key，三跳网络才落一条事实。

**5. 计费简单且可预测。** count-based，非按 GB：$0.25/千 events 写入、$0.75/千 records/月
（内置策略）或 $0.25/千（override 与自管）、$0.50/千次检索调用
（[定价页](https://aws.amazon.com/bedrock/agentcore/pricing/)，与 2026 年中一致）。
官方示例：10 万 events + 1 万 records + 2 万次检索 ≈ $42.50/月。自管策略的模型费另计。

**6. 策略类型齐全。** userPreference、semantic、summarization，加 2026 年 1 月推出的
**episodic**（带 reflection 配置），以及内置策略 override 与 `usingSelfManaged`。
> devguide 的 long-term-memory 页面仍只列三种，未含 episodic —— 以
> [launch 博客](https://aws.amazon.com/blogs/machine-learning/build-agents-to-learn-from-experiences-using-amazon-bedrock-agentcore-episodic-memory/)
> 为准。CDK 构造把策略枚举标为 experimental，那是 CDK alpha 模块状态，不等于服务状态。

## 二、共享记忆的治理：一个普遍空缺

逐个核实七家的共享原语后，结论是：**没有一家在写入变为他人可见之前设置审批闸门。**

- **mem0**：`user_id`/`agent_id`/`run_id` 作用域组合，`org_id`/`project_id` 作租户容器 ——
  作用域放宽，无审核环节。
- **Zep**：写入独立 Graph（当前文档用 "Graph" vs "User Graph"，不再叫 group graph）——
  未设闸。
- **Letta**：`shared_block_ids` —— "When one agent updates the block, **all others see
  the change immediately**"，明确事后策展（"Any agent can append learnings"）。有只读
  block，是这组里最接近闸门的东西，但那是读写标志，不是审核流。
- **Databricks**：scope + Unity Catalog ACL 与审计 —— 写入未设闸。
- **Vertex Memory Bank**：`direct_memories_source` 允许"你的 agent **或 human-in-the-loop**
  负责抽取"，是唯一在托管服务里为人工环节留出钩子的 —— 但那是**抽取**环节的钩子，不是
  可见性之前的审批，且预抽取事实每次调用上限 5 条。
- **Foundry**：scope + 记忆逐条 CRUD（预览）。微软自己关于记忆投毒的文章给的是事后与
  防御性建议，并指出"scoped to one authenticated user 与 scoped to a team/tenant 的风险
  画像截然不同"。
- **LangGraph/LangMem**：本轮未单独核实，按未核实处理。

> 因此本蓝图填补的是一个被多方独立指出、但无人产品化的空缺。这一判断的完整依据见
> [下一步演进](下一步演进.md)的定位说明一节。

## 三、本蓝图的放大效应

叠加在 AgentCore 上，治理设计与平台能力产生了三处相互增强，而非简单相加。

**1. 治理条件进入检索路径，而非事后筛选。**
`src/agent/context_builder.py` 用 `project_id` + `review_status=approved` 两个元数据
过滤器检索共享记忆。在预过滤架构下，这意味着**未批准、被驳回、被取代的记录根本不参与
相似度竞争** —— 不是算完分再滤掉。于是"只检索已审知识"从应用层约定变成了检索层的结构性
保证，同时因候选集更小而获得精度收益（devguide 用词："measurably better accuracy"）。

**2. 逐字入库把 AgentCore 的最大短板转成了非问题。**
共享层批准后走 `BatchCreateMemoryRecords` 直接写入，不经二次抽取。这带来两个结果：
一是审核员批准的文本与入库文本逐字节一致，审计链成立；二是**AgentCore 抽取质量在共享层
完全不构成风险**，因为共享层不使用抽取。而对个人层，抽取质量下降的后果被 IAM 限制在单个
actor 内。换言之，平台抽取能力的不确定性被分层设计隔离在低风险区域。

**3. 用离散状态标志实现取代，绕开了平台的空白与业内的公共难题。**
AgentCore 没有失效语义（见上文的文档矛盾），Zep 有但需换栈。本蓝图的方案是：审核员批准
一条带 `supersedes` 的候选项时，用 `BatchUpdateMemoryRecords` 把旧记录的 `review_status`
翻成终态，它随即**离开可检索集合**（因为检索按 `review_status=approved` 预过滤），而记录
本身保留以供审计。

这一步刻意**不引入 LLM 裁决器**。业内在这件事上的成绩是负面的：某图式记忆系统的冲突消解
得分是其最低类别，恰因矛盾判断是一次 LLM 调用
（[arXiv:2606.01435](https://arxiv.org/html/2606.01435)）；关于陈旧知识的研究报告称前沿
模型对隐式失效处理不佳，且常直接接受问题中嵌入的陈旧前提
（[arXiv:2605.06527](https://arxiv.org/abs/2605.06527)）。本蓝图已有带审计链的人工决策
点，扩展它的代价是一个字段加一个工作流分支。

**成本上的务实性。** 治理链路本身几乎不增加 Memory 费用：审核只发生在候选项上，而候选项
存在 DynamoDB；共享记录数量以"团队沉淀的结论"计，通常是个人记忆的极小比例。真正的成本
在 FM 推理，而共享层不做抽取，等于省掉了这部分。

## 四、务实结论：什么时候该选什么

**选 AgentCore + 本蓝图**：多用户共用一个 agent、团队知识需要问责、已在 AWS、合规要求
可审计的跨会话权威。核心理由是隔离由平台强制、写入路径可设闸。

**选 mem0 / Zep**：单用户或弱隔离场景、检索质量优先、需要 hybrid 或关键词精确匹配、
不绑云。Zep 另有 Fact Invalidation 这一 AgentCore 缺失的能力。

**分层组合最务实。** 本蓝图的四层知识分层允许个人层与共享层用不同后端：个人偏好层可换成
mem0/Zep 以取得更好的抽取与检索，共享层保留 IAM + 审核的治理属性。检索优先级铁律不因
个人层换实现而失效。

**需要关键词精确匹配时（工单号、错误码、SKU），不要硬塞进 Memory。** 语义检索本就不擅长
此类。正确去处是 Knowledge Base 层 —— Bedrock KB 支持 hybrid，而分层设计已经为这个需求
预留了位置。这是分层的实际收益：能力缺失可以被安置，而不必扭曲某一层的用途。

- AgentCore consolidation 是否存在**未文档化**的 INVALID 内部状态。AWS 博客与 API 文档
  互相矛盾，本蓝图按 API 文档行事，不依赖该行为。建议向服务团队确认。
- episodic 策略无明确的 "GA" 声明文档，按 launch 博客处理。
- LangGraph/LangMem 的共享原语本轮未核实。
- mem0 那三个 CVE 是否已有修复版本未能确认：被引为修复的 commit 实为脆弱 HEAD，一手来源
  给的缓解手段是网络隔离与鉴权反代。
